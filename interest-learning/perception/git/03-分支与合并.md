## 1. 分支的本质：一个会移动的指针

先纠正一个直觉误区：**新建分支不会复制一份代码**，它只是新建了一个小标签（指针），指向某一条提交。

| 名词 | 是什么 | 通俗理解 |
|------|--------|---------|
| `main`（或 `master`） | 默认主分支名 | 主干道 |
| 分支 branch | 指向某次提交的可移动指针 | 便签纸，贴在某个存档点上 |
| `HEAD` | "我现在站在哪"的指针 | 你的当前站位，通常指向某个分支 |

```text
              ┌──────────┐   ┌──────────┐
              │ 提交 A   │──►│ 提交 B   │
              └──────────┘   └────┬─────┘
                                  │  main 和 feature 都指向 B
                       main ──────┤
                    feature ──────┘

   在 feature 上提交一次后：
              A ──► B ──► C(新提交)
                    ▲      ▲
                  main   feature(HEAD)
```

> 💡 类比：Git 的历史像一条**地铁线路图**，分支就是"岔出去的一条支线"。你可以在支线上随便试错（写新功能、试新算法），试成了就并回主线，试失败了直接把支线剪掉，主线一点没受影响。

## 2. 三板斧：建、切、合

```bash
# 建分支（新指针指向当前提交）
git branch feature-detect

# 切分支（Git 2.23+ 推荐用 switch，语义更清楚）
git switch feature-detect

# 建并立刻切过去（最常用的一条）
git switch -c feature-detect

# 看看有哪些分支、我现在在哪（* 号表示当前位置）
git branch

# 合并：先切回目标分支，再把别的分支并进来
git switch main
git merge feature-detect
```

> 💡 `git checkout` 和 `git switch` 都能切分支，`switch` 是 Git 2.23 新加的、**只干切分支**这件事的命令；`checkout` 老命令还能顺手还原文件（第02讲的 `git checkout -- 文件`），功能杂容易搞混，新代码建议用 `switch`。

合并有两种情况：

| 情况 | 结果 | 说明 |
|------|------|------|
| 快进合并（fast-forward） | 直接让 `main` 指针往前滑到 `feature` | 主分支在分叉后没提交过新东西，最省事 |
| 三方合并（3-way merge） | 自动生成一个"合并提交（merge commit）" | 两边都有新提交，Git 自动把改动拼起来 |

## 3. 冲突：同一行被两边改了

Git 很聪明，能自动合并**不同文件**、**同一文件的不同区域**的改动。它处理不了的只有一种情况：**同一行（或紧邻的几行）被两边各自改了**，它不知道该听谁的，于是停下来让你决定。

```text
<<<<<<< HEAD
speed_limit = 30        ← 你当前分支（main）的版本
=======
speed_limit = 45        ← 被合并分支（feature-detect）的版本
>>>>>>> feature-detect
```

三个标记的含义必须记住：

| 标记 | 含义 |
|------|------|
| `<<<<<<< HEAD` | 冲突开始，下面是**你当前所在分支**的内容 |
| `=======` | 分隔线，上下两份内容的分界 |
| `>>>>>>> 分支名` | 冲突结束，上面是**要被合并进来的分支**的内容 |

解决冲突三步骤：

```bash
git merge feature-detect
# 1) 打开有冲突的文件，手动改成你想要的样子（把 <<<<<<<、=======、>>>>>>> 三行全删掉）
# 2) 重新标记为已解决
git add detect.py
# 3) 提交，完成合并
git commit            # 或 git commit -m "merge: 合并 feature-detect 并解决冲突"
```

> ⚠️ 常见坑：
> 1. 改完忘了 `git add` 就 `git commit`，Git 会拒绝你，提示存在未解决的冲突。
> 2. 千万别把 `<<<<<<<`、`=======`、`>>>>>>>` 这些符号留在代码里提交上去——代码会直接跑不起来。
> 3. 冲突时慌手慌脚删错内容？`git merge --abort` 一键回到合并前的状态，很安全。

> ⚠️ 什么年代了还怕冲突：**冲突不是错误，是 Git 在请你做人类决策。** 冲突越早解决越好，分支开得越久、改动越大，冲突越难收拾。

## 4. rebase：一句话版

`git rebase main` = **把你这条分支上的提交"揭下来"，重新一条条贴到 main 的最新提交之后**，让历史变成一条直线，而不是有分叉和合并提交的"麻花"。

| 对比 | `merge` | `rebase` |
|------|---------|----------|
| 历史形状 | 保留分叉，多了合并提交 | 拉成一条直线，更整洁 |
| 安全性 | 安全，不改历史 | 改写提交哈希，**不要对已 push 的公共分支用** |
| 一句话 | 把两条线"缝"在一起 | 把自己的提交"搬"到别人后面 |

## 🎯 课后练习（约8分钟）

```bash
mkdir -p ~/git-branch && cd ~/git-branch
git init
git config user.name "你的名字"; git config user.email "你@example.com"

# 1. 主分支上先有一次提交
echo "车道线识别 v1" > lane.py
git add lane.py && git commit -m "feat: 车道线识别初版"

# 2. 建一条新分支并在上面干活
git switch -c feature-obstacle
echo "障碍物检测 v1" >> lane.py        # 故意改同一文件
git add lane.py && git commit -m "feat: 增加障碍物检测"

# 3. 回到 main，也改同一个文件（制造冲突）
git switch main
echo "主分支改的同一行" >> lane.py
git add lane.py && git commit -m "fix: 主分支上的修正"

# 4. 合并 → 触发冲突
git merge feature-obstacle

# 5. 看冲突长什么样
cat lane.py
# 6. 手动编辑解决（删掉三个标记行，保留你要的内容），然后
git add lane.py
git commit -m "merge: 解决 lane.py 冲突"
git log --oneline --graph
```

> ✅ 你应该看到（类似）：
> ```
> Auto-merging lane.py
> CONFLICT (content): Merge conflict in lane.py
> Automatic merge failed; fix conflicts and then commit the result.
>
> <<<<<<< HEAD
> 主分支改的同一行
> =======
> 障碍物检测 v1
> >>>>>>> feature-obstacle
>
> *   8a9b0c1 (HEAD -> main) merge: 解决 lane.py 冲突
> |\
> | * 3d4e5f6 (feature-obstacle) feat: 增加障碍物检测
> * | 7c8d9e0 fix: 主分支上的修正
> |/
> * 1a2b3c4 feat: 车道线识别初版
> ```
> （看到 `|\ / |` 这种分叉图形，就说明三方合并成功了）

## 本讲小结

| 概念 | 要点 |
|------|------|
| 分支 branch | 指向某次提交的可移动指针，不复制文件 |
| `git switch -c xx` | 新建并切换到分支 |
| `git branch` | 列出分支，`*` 是当前分支 |
| `git merge xx` | 把 xx 合并进当前分支 |
| 快进 / 三方合并 | 无分叉则指针前移；有分叉则产生合并提交 |
| 冲突产生条件 | 同一行被两边各自修改 |
| `<<<<<<<` / `=======` / `>>>>>>>` | 当前分支内容 / 分界 / 对方分支内容 |
| 解决冲突 | 手动改 → `git add` → `git commit`（慌了就 `git merge --abort`） |
| `git rebase` | 把自己的提交搬到别人最新提交之后，历史变直线；别对已 push 的公共分支用 |
