## 1. remote 与 origin

`remote`（远程仓库）就是"云端那份仓库的地址簿"，`origin` 只是给这个地址起的**默认昵称**（叫别的也行，但大家都习惯叫 origin）。

```bash
# 查看当前关联了哪些远程仓库
git remote -v
# ✅ 你应该看到：
# origin  git@github.com:whut-baja/perception.git (fetch)
# origin  git@github.com:whut-baja/perception.git (push)

# 给本地仓库绑定一个远程地址（第一次才要做）
git remote add origin https://github.com/whut-baja/perception.git

# 第一次把本地 main 推上去，并建立跟踪关系（之后直接 git push 就行）
git push -u origin main
```

> 💡 类比：`origin` 就像手机通讯录里的"家里"——真正的号码是那一长串 URL，`origin` 只是你给它的备注名。打给"家里"就等于打给那个号码。

| 命令 | 作用 |
|------|------|
| `git clone <地址>` | 第一次把整个仓库下载到本地（含全部历史），自动配好 origin |
| `git fetch` | 只下载远程的新提交，**不合并**，安全 |
| `git pull` | `fetch` + `merge`，下载并合并进当前分支（日常最常用） |
| `git push` | 把本地提交上传到远程 |

> 💡 团队日常节奏：**每天开工先 `git pull`，写完一段就 `commit`，收工前 `push`。**

## 2. .gitignore：哪些东西不该提交

有些文件是"本机专属"或"自动生成"的，提交上去只会污染仓库、引发冲突：编译产物、依赖目录、IDE 配置、虚拟环境、数据集与模型权重、日志与临时文件。

在仓库根目录建一个 `.gitignore`（注意前面有个点），一行写一条规则：

```gitignore
# ---------- Python ----------
__pycache__/
*.py[cod]
.venv/
venv/
*.egg-info/
.ipynb_checkpoints/

# ---------- Node ----------
node_modules/
dist/
.next/
*.log
npm-debug.log*

# ---------- Java ----------
target/
*.class
*.jar
.gradle/
build/

# ---------- 编辑器 / 系统 ----------
.idea/
.vscode/
.DS_Store
Thumbs.db

# ---------- 项目专属：图片数据集和模型权重不要传 ----------
dataset/
*.onnx
*.pt
*.weights
```

> ⚠️ 常见坑：**已经被 Git 跟踪过的文件，后加进 `.gitignore` 是不生效的**。要先把跟踪关系删掉：
> ```bash
> git rm --cached config.local.yaml   # 只从 Git 里删，本地文件保留
> git commit -m "chore: 停止跟踪本地配置"
> ```
> 另外，**密码、密钥、token 绝对不能提交**——一旦进了远程仓库历史，删掉也很难彻底清干净，等于泄露。

## 3. commit message 规范

提交说明不是写给自己看的，是写给三个月后的队友（和三个月后的你）的。约定式提交（Conventional Commits）最常用的几个前缀：

| 前缀 | 含义 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat: 增加锥桶颜色分割节点` |
| `fix` | 修 Bug | `fix: 修正摄像头索引写死导致打不开的问题` |
| `docs` | 只改文档 | `docs: 补充 README 的运行环境说明` |
| `refactor` | 重构，不改功能 | `refactor: 把图像预处理抽成独立函数` |
| `chore` | 杂活（依赖、配置） | `chore: 升级 opencv-python 到 4.10` |
| `test` | 加/改测试 | `test: 补充 HSV 阈值分割单元测试` |

> 💡 类比：commit message 就像**病历上的诊断记录**——"患者发烧"没人能看懂，要写"术后第 3 天，切口轻度红肿，已换药"。好的提交说明要让队友不用看代码就知道你干了什么。

> ⚠️ 反例（不要这样写）：`更新`、`改了一下`、`123`、`aaa`、`最终版`、`.`。

## 4. PR 流程五步

PR（Pull Request，GitHub 叫法；Gitee 叫 PR / 合并请求）＝ "我这条分支写好了，请大家审查后合并进主分支"。

| 步骤 | 做什么 | 命令 / 操作 |
|------|--------|------------|
| ① 拉最新 + 建分支 | 别直接改 `main`，先切一条功能分支 | `git switch main && git pull`<br>`git switch -c feat/obstacle-detect` |
| ② 提交并推送 | 小步提交，写清 message，推到远程 | `git add . && git commit -m "feat: 障碍物检测"`<br>`git push -u origin feat/obstacle-detect` |
| ③ 开 PR | 网页上点 "New Pull Request"，写清**改了什么、为什么改、怎么测的** | 描述里可贴效果图/截图 |
| ④ 评审与修改 | 队友评论后，同分支继续提交并 push，PR 会自动更新 | `git push`（不用重开 PR） |
| ⑤ 合并并清理 | 通过后由维护者点 Merge，删掉已合并的分支 | `git switch main && git pull`<br>`git branch -d feat/obstacle-detect` |

> 💡 类比：PR 就像**论文的同行评审**——你不是直接把自己的段落塞进全组的论文，而是先贴出来说"我这段这么写，大家看看"，改到大家都点头了才合进去。

> ⚠️ 铁律：**永远不要在 `main` 上直接开发再 push。** 主分支必须随时是能跑的版本，出了事故没人能追责到具体改动。

## 5. 多人同时改同一个文件怎么办

1. **从源头上减少冲突**：动手前先 `git pull`；按模块/文件分工（你写 `detect.py`，我写 `camera.py`）；不要一个人重排整个文件的格式。
2. **小步提交、频繁推送**：憋一周再合并 = 冲突地狱。
3. **真的撞车了**：按第03讲的流程解开冲突（`<<<<<<<` → 手动改 → `git add` → `git commit`），改完 `git push`。
4. **解不开、改乱了**：`git merge --abort` 或 `git rebase --abort` 撤退，然后找队友当面核对，别硬刚。
5. **改错了但你还没 pull**：`git pull` 时提示本地有未提交修改无法合并 → 先 `git stash`，pull 完再 `git stash pop`。

## 6. 队友把仓库搞乱了怎么救：reflog

`reflog` 是 Git 的"操作录像机"：**HEAD 每一次移动（commit / reset / rebase / merge / switch）都会被记录下来**，哪怕那个提交已经不在任何分支上了。它默认保留 90 天。

```bash
# 查看"我最近都干了啥"
git reflog

# ✅ 你应该看到（类似）：
# 8a9b0c1 (HEAD -> main) HEAD@{0}: reset: moving to HEAD~1
# 3d4e5f6 HEAD@{1}: commit: feat: 增加障碍物检测     ← 被 reset 掉的那条提交还在！

# 救回来：直接切到那个提交
git reset --hard 3d4e5f6          # 恢复成那次提交的状态
# 或者更稳的做法：新开一个分支指向它，避免再次误伤
git branch rescue 3d4e5f6
```

> 🎯 一句话原则：**只要曾经 `commit` 过，几乎都能救回来；从没 `commit` 过的改动，`--hard` 和 `restore` 抹掉就真没了。**

> 💡 类比：`reflog` 像**回收站**——文件删了别急着哭，先去回收站翻一翻。但注意：**没保存过的草稿，回收站里也不会有。**

## 🎯 课后练习（约7分钟）

```bash
# 1. 本地建仓库并加 .gitignore
mkdir -p ~/git-team && cd ~/git-team
git init
git config user.name "你的名字"; git config user.email "你@example.com"

printf '__pycache__/\n*.pyc\n.venv/\nnode_modules/\n.idea/\n*.log\n' > .gitignore

# 2. 写代码 + 规范提交
echo "print('perception')" > detect.py
echo "临时日志" > debug.log
git add .gitignore detect.py
git commit -m "feat: 增加检测脚本与 gitignore"

# 3. 验证 ignore 是否生效（debug.log 不应出现在列表里）
git status --short
git check-ignore -v debug.log

# 4. 体验 reflog 救人
echo "重要功能" >> detect.py
git add detect.py && git commit -m "feat: 重要功能"
git reset --hard HEAD~1        # 假装误操作把提交删了
git reflog                     # 找到那条提交的哈希
git reset --hard HEAD@{1}      # 用 reflog 里的位置把它救回来
cat detect.py                  # ✅ 应该又能看到"重要功能"
```

> ✅ 你应该看到（类似）：
> ```
> A  .gitignore
> A  detect.py
> .gitignore:6:*.log	debug.log          ← 说明 debug.log 被成功忽略
> HEAD is now at 1a2b3c4 feat: 增加检测脚本与 gitignore
> 重要功能
> ```

## 本讲小结

| 概念 | 要点 |
|------|------|
| `remote` / `origin` | 远程仓库地址 / 它的默认昵称 |
| `git clone` | 第一次下载整个仓库（含历史） |
| `git fetch` vs `git pull` | fetch 只下载不合并；pull = fetch + merge |
| `.gitignore` | 屏蔽编译产物、依赖、IDE 配置、数据集、密钥等；已跟踪的文件需 `git rm --cached` |
| commit 前缀 | `feat` / `fix` / `docs` / `refactor` / `chore` / `test`，一句话说清"做了什么" |
| PR 五步 | 拉最新建分支 → 提交推送 → 开 PR → 评审修改 → 合并删分支 |
| 多人改同一文件 | 先 pull、按模块分工、小步提交；冲突手动解开或 abort 重来 |
| `git reflog` | 操作录像机/回收站，能救回被 reset 掉的提交（前提是曾 commit 过） |
| 铁律 | 不直接改 `main`；不提交密钥；不用 `--hard` 前不 `status` |
