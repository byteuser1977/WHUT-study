# 第04讲：方案设计实战（正文约12分钟 + 练习约18分钟）

## 你将学到
- 一套能套用到任何感知项目的方案设计模板：需求 → 传感器 → 流水线 → 算力预算 → 降级 → 测试 → 指标
- 每一步该问自己什么问题、该产出什么数字
- 一份完整的示例方案（可直接模仿改写）
- 一份算力预算表的填法与降级策略清单

## 1. 需求分析：先把数字定下来

**需求分析**是把"我们要做个感知系统"这句空话，变成一串能验收的数字。别急着选相机、别急着找模型，先回答这 6 个问题：

| 要问的问题 | 为什么要问 | 巴哈场景示例取值 |
|-----------|-----------|------------------|
| 车速范围多少？ | 决定最低帧率与检测距离 | 0~50 km/h（≈14 m/s） |
| 需要多远的检测距离？ | 决定相机焦距、分辨率、能否发现小目标 | 行人 ≥15 m，锥桶 ≥20 m |
| 有效制动距离多少？ | 决定允许的端到端延迟上限 | 刹车距离约 4 m，故延迟 ≤100 ms |
| 要识别哪些目标？ | 决定算法类别数与难点 | 可行驶区域、行人、物块、锥桶 |
| 赛道宽度多少？ | 先验约束要用（宽度约束/消失点） | 有效路面 3~6 m |
| 全天候还是仅白天？ | 决定是否上红外/补光灯/雷达 | 白天为主，需支持扬尘与逆光；夜间可选 |

> 💡 类比：需求分析就像装修前先量房。不量房就买家具，最后沙发要么进不了门、要么空出一大块。**数字没定下来就选传感器，是 90% 项目返工的起点。**

## 2. 传感器选型与安装位置

| 方案 | 能提供 | 优点 | 缺点 | 适合巴哈吗 |
|------|--------|------|------|-----------|
| 单目相机 | 2D 图像、纹理、颜色 | 最便宜、最省电、信息最丰富 | 无绝对尺度、测距靠假设（地面平面） | ✅ 主力，必装 |
| 双目相机 | 视差 → 深度 | 有深度、能算尺寸和距离、成本适中 | 需要纹理；颠簸后标定易漂、算力开销大 | ⚠️ 首选升级项 |
| 深度相机（RGB-D，如 RealSense） | 像素级距离 | 直接给几何信息，绕开颜色 | 强光/阳光下红外结构光失效；量程短 | ⚠️ 遮光条件下可用 |
| 激光雷达 LiDAR | 精确点云 | 不受光照影响、测距准、可做地面分割 | 贵、功耗高、无纹理、扬尘/雨雾有衰减 | ⚠️ 有预算就上，作为几何真值 |
| 毫米波雷达 | 距离+相对速度 | 穿透扬尘雨雾、测速准、便宜 | 角分辨率低、无法区分物体形状 | ✅ 补"运动目标"这一维度 |

**安装位置的三条经验**：
1. **高度**：离地 0.8~1.2 m（"高到不被泥点糊住、低到能看清近处地面"的折中，别贴地装）。
2. **角度**：镜头略向下俯 5°~15°，让近处 3~15 m 的有效路面占据图像下半部——那里是行车最需要的区域。
3. **防护**：加遮光罩（挡逆光）、加偏振片（压水面反光）、加吹气/雨刷（清泥点），并保证**减振安装**（橡胶垫），颠簸时图像才不至于全靠算法救。

> ⚠️ 常见坑：把相机装在最前端的防撞梁上"视野最好"。结果一撞就歪（外参全废）、泥水直接糊镜头、晒得最烫。**感知硬件的安装位置是"生存性"和"视野"的折中，不是越靠前越好。**

## 3. 算法流水线

```text
[相机采集 60fps]
      ↓
① 预处理：去畸变(标定参数) → 降分辨率/ROI裁剪 → CLAHE光照归一化 → 中值滤波
      ↓
② 可行驶区域识别：HSV自适应阈值 + Sobel梯度 + LBP纹理 → 三路投票
      ↓
③ 障碍物检测：颜色法(锥桶) ∥ 轻量检测网络(行人/物块) → NMS去重
      ↓
④ 后处理：时域5帧投票 + 最大连通域 + 宽度/消失点约束 + ByteTrack跟踪
      ↓
⑤ 输出到 ROS 2：/perception/drivable_area (PolygonStamped)
                /perception/obstacles    (BoundingBoxArray)
                /perception/status       (诊断信息：帧率、模块心跳)
```

第 ⑤ 步的**诊断话题**常被新手忽略：它让控制组和调试的人能一眼看到"感知卡了还是瞎了"。**没有诊断输出的感知模块，等于一个黑盒，出事时无法定位。**

## 4. 算力预算表

**算力预算**就是提前把每一阶段的毫秒数分配好，写完代码再对照检查，超了就优化，而不是等整体跑不动了才知道。

| 阶段 | 预算耗时 | 累积 | 超预算时的优化手段 |
|------|----------|------|-------------------|
| 采集 + 去畸变 | 3 ms | 3 ms | 查表法去畸变 / 硬件 ISP 校正 |
| 降分辨率 + ROI 裁剪 | 2 ms | 5 ms | 直接用相机硬件输出小分辨率 |
| CLAHE 光照归一化 | 3 ms | 8 ms | 缩小 tile 数 / 只对 ROI 做 |
| 可行驶区域（三路特征） | 8 ms | 16 ms | 切到单通道灰度、隔行采样 |
| 障碍物检测（YOLOv8n INT8） | 25 ms | 41 ms | 降到 416 输入 / 提高到 INT8 纯量化 |
| 跟踪 + 时域滤波 | 5 ms | 46 ms | 减小搜索窗、隔帧跟踪 |
| 后处理 + ROS 2 发布 | 4 ms | 50 ms | 复用消息对象，避免反复分配内存 |
| **总计** | **50 ms** | — | 目标 ≤60 ms，含抖动余量 |

> 💡 类比：算力预算就像出门前给行李箱分配重量。总重超了，你得知道"到底是哪一层塞多了"才能有针对性地减。**没有预算表的优化，全靠感觉，最后一定是把最关键的那块砍掉。**

## 5. 降级策略：一定会坏，坏要坏得可控

**降级（degradation）**指某个模块失效时，系统退到一个更弱但仍能工作的模式，而不是直接死掉。

| 失效场景 | 检测方式 | 降级动作 |
|----------|----------|----------|
| 算力不足、帧率跌破 10 FPS | 统计帧间隔时间 | 关掉 CLAHE 与学习法分支，切"几何+颜色"轻量模式；仍不足则只跑锥桶+ROI 极限裁剪 |
| 相机失效 / 图像全黑全白 | 帧方差 ≈ 0、连续 N 帧无变化 | 切到雷达/毫米波几何检测（若有）；否则输出"感知不可用"状态位 + 触发限速提示 |
| 极端光照（过曝/全黑） | 直方图饱和像素占比 > 30% | 切换相机曝光档位（自动曝光收敛前用保守参数）；启用上一帧的"冻结结果" + 置信度置低 |
| 扬尘/隧道短暂遮蔽 | 图像对比度过低 | 切时域预测模式（沿用上一帧结果平移推算），恢复后自动切回 |
| 前车扬尘遮挡 + 相机脏污 | 全局对比度骤降 | 触发镜头吹气/提醒停车清洁；同时输出"置信度低"标记 |

**关键原则：任何降级都必须输出"我现在不在正常状态"的标记**，让控制组知道该减速。**静默失效是感知系统最危险的失效方式。**

## 6. 测试方案：四层递进

| 层级 | 在哪测 | 测什么 | 出口标准 |
|------|--------|--------|----------|
| ① 离线回放 | 电脑 | 用已采集的视频/图片集跑算法，算指标 | 在测试集上召回率达标 |
| ② 仿真 | 电脑（Gazebo/CARLA 自定义场景） | 极端工况批量复现（逆光、夜间、扬尘、颠簸） | 各工况下指标不低于阈值 |
| ③ 封闭场地 | 校内空地摆锥桶 | 真实相机 + 真实振动 + 真实光照 | 连续运行 30 min 无崩溃，帧率稳定 |
| ④ 实车 / 极端天气 | 赛道实跑 | 泥水、扬尘、坡道、雨天 | 关键工况无致命漏检，输出降级正确 |

## 7. 评估指标

| 指标 | 定义 | 目标值 |
|------|------|--------|
| 帧率 FPS | 每秒完成完整流水线的次数 | ≥20（下限 10） |
| 端到端延迟 | 从曝光到发出 ROS 2 消息的时间 | ≤60 ms |
| 召回率 Recall | 真实目标被检出的比例（查全） | 行人 ≥95%，锥桶 ≥95%，物块 ≥80% |
| 误报率 FPR | 误检目标数 / 总检测数（查准的反面） | ≤10% |
| 失效里程 | 连续行驶中感知输出不可用的总距离 | ≤总里程 2%（且每次 <3 s） |
| 恢复时间 | 从失效到恢复正常输出的耗时 | ≤1 s |

> ⚠️ 常见坑：只报"平均准确率 92%"。平均值会掩盖最危险的场景（行人漏检）。**安全类指标的报法必须是"最差工况下的值"，不是平均值。**

## 8. 示例方案（约 300 字，可模仿改写）

> **赛道感知系统设计（示例）**
>
> 需求：巴哈越野赛道，车速 0~50 km/h，需识别可行驶区域、行人、物块、高锥桶，行人检测距离 ≥15 m，端到端延迟 ≤60 ms。
>
> 传感器：车顶遮光罩下单目全局快门相机 1280×720@60fps，离地 1.0 m、俯角 10°；预留双目与毫米波雷达接口作为二期升级。
>
> 流水线：去畸变 → 下半部 ROI 裁剪至 640×360 → CLAHE 光照归一化 → 三路特征（HSV 自适应阈值 + Sobel 梯度 + LBP 纹理）投票得到可行驶区域；YOLOv8n 经 INT8 量化与 TensorRT 加速，抽帧 15 FPS 检测行人/物块，HSV 橙色阈值并行检锥桶；ByteTrack 补帧至 30 FPS；5 帧时域投票 + 最大连通域 + 赛道宽度与消失点约束过滤误检；结果经 ROS 2 话题发给控制组，并附带诊断状态。
>
> 算力预算 50 ms（目标 ≤60 ms）。降级策略：帧率跌破 10 FPS 时关闭学习法分支；相机失效时输出不可用状态位并建议限速。
>
> 测试：离线回放 → 仿真极端工况 → 封闭场地 30 分钟 → 赛道实跑。指标目标：帧率 ≥20 FPS，行人召回 ≥95%、误报 ≤10%，失效里程 ≤2%。

## 🎯 课后练习（约18分钟）

1. **写需求表**：把第 1 节的 6 个问题填上你自己设定的数值（可以合理假设），并说明每个数值是怎么推出来的。
2. **画流水线**：用文字框图画一遍你的流水线，标出每步的输入输出格式。
3. **填算力预算表**：给自己设一个总预算（如 60 ms），分配到各阶段，算出累积值。若超了，写出你打算砍哪一步、为什么砍它。
4. **写降级策略**：至少写 3 条"失效场景 → 检测方式 → 降级动作"。
5. **写 300 字示例方案**：照第 8 节的格式，写一份属于你自己的完整方案。

**自检清单（对照勾选）**：

```text
[ ] 需求里有具体数字（车速、距离、延迟、目标类别）
[ ] 传感器写了型号量级 + 安装高度/角度 + 防护措施
[ ] 流水线每一步都有明确的输入输出，并指明最终发布到哪个 ROS 2 话题
[ ] 算力预算所有阶段加起来 ≤ 你设定的总预算
[ ] 降级策略里每条都输出了"我处于降级状态"的标记
[ ] 测试方案覆盖了仿真 / 封闭场地 / 实车 / 极端天气
[ ] 指标里区分了"平均值"与"最差工况值"，安全项用后者
```

> ✅ 你应该看到：一份 1~2 页、全是数字和可复现步骤的设计文档。**面试时掏出来，比说"我会用 YOLO"有用十倍。**

## 本讲小结

| 步骤 | 核心产出 | 最容易犯的错 |
|------|----------|--------------|
| 需求分析 | 车速/距离/延迟/目标类别的具体数字 | 还没定数字就选传感器 |
| 传感器选型 | 型号量级 + 安装高度角度 + 防护 | 相机贴地装、装在最前端 |
| 算法流水线 | 预处理→可行驶区域→障碍物→后处理→ROS 2 + 诊断话题 | 无诊断输出，变黑盒 |
| 算力预算 | 各阶段毫秒分配表，总和 ≤ 总预算 | 没预算，优化靠感觉 |
| 降级策略 | 失效场景→检测→降级动作，且输出状态标记 | 静默失效（最危险） |
| 测试方案 | 离线→仿真→封闭场地→实车四层 | 只测晴天直道 |
| 评估指标 | FPS/延迟/召回/误报/失效里程，安全项看最差工况 | 只报平均准确率 |
