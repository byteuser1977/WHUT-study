## 1. 先搞清楚：巴哈赛道不是马路

中国大学生巴哈大赛（Baja SAE China，一项面向大学生的越野赛车设计与制造赛事）的赛道，是一条**野地赛道**：路面由土、砂、碎石、草皮、泥浆临时堆出来，一圈几百米到一两公里，赛前才用推土机大致整平，比完就拆。

它和我们天天见的城市道路有本质区别：

| 维度 | 城市道路 | 巴哈赛道 |
|------|----------|----------|
| 边界 | 白色实线/虚线、路沿石 | 基本没有标线，靠土色与草色自然分界 |
| 路面材质 | 沥青/水泥，反射率稳定 | 土、砂、泥、草、积水混合，反射率随机变 |
| 光照 | 相对均匀，有路灯 | 强逆光、树影、扬尘散射、夜间无照明 |
| 平整度 | 毫米级 | 厘米到十厘米级，车会跳起来 |
| 可用算力 | 笔记本/服务器 | 一块几十瓦的边缘计算板 |
| 维护 | 有人清障 | 扬尘、泥点自己往镜头上糊 |

> 💡 类比：城市道路识别像"在图书馆里找一本按编号排好的书"——有规矩、有编号、光线稳定。巴哈赛道识别像"在台风天的菜市场里找一个穿着迷彩服的人"——目标还在，但所有让你认路的线索（颜色、边缘、亮度）都在剧烈变化。

## 2. 赛道对视觉的 8 种"刁难"

我们把赛道上会遇到的恶劣工况列成一张表。**这张表就是本大类的总纲**，后面三讲都在逐条对付它们。

| # | 工况 | 现象 | 对视觉算法的破坏 |
|---|------|------|------------------|
| 1 | 赛道边界模糊 | 土路与草地是渐变过渡，没有白线 | 边缘检测找不到连续边缘；基于"找两条车道线"的算法直接失效 |
| 2 | 可行驶路面被泥水掩盖 | 一段路面被泥浆盖住，颜色变成深褐 | 靠"路面是灰白色"的颜色阈值整块判错 |
| 3 | 扬尘 | 前车扬起的尘土变成一片半透明雾 | 图像对比度骤降，远处细节消失，看起来像"白墙" |
| 4 | 强光/逆光/阴影 | 逆光时路面全黑、天空全白；树影出现硬边界 | 全局阈值彻底失效；阴影边界被误当成赛道边界 |
| 5 | 夜间 | 只能靠车灯照明，光照极度不均匀 | 只有光斑范围内有信息，其余全黑 |
| 6 | 生水与反光 | 积水像镜子一样反射天空 | 一块高亮区域被误判为"障碍物"或"天空" |
| 7 | 颠簸与车体振动 | 车轮跳起、车身抖动 | 图像运动模糊、相邻帧画面剧烈跳动，时域滤波被打乱 |
| 8 | 算力与电源受限 + 相机装得低 | 边缘板功耗几十瓦；相机离地不到 50 cm | 无法跑大模型；镜头容易被泥点、水花糊住 |

> ⚠️ 常见坑：很多人第一次上车就把相机装在车头最低处（以为"看得清地面"）。结果一场比赛下来镜头糊满泥点，图像变成一片花。**安装位置要把"视野"和"生存"一起考虑**——抬高一点、加个遮光罩/雨刷、加个吹气装置，都比"离地最近"划算。

## 3. 为什么实验室方案一到赛道就失效

在实验室里，你对着几张固定的照片调 HSV 阈值，调到"效果好得不得了"，准确率 95%。到了赛道，召回率掉到 40%。原因不是代码写错了，而是踩了三个工程大坑：

1. **数据集过拟合（domain shift，域偏移）**：训练/调参用的图像和现场图像来自完全不同的"数据分布"。实验室是恒温白光、干净路面；赛道是斜射阳光、泥浆路面。输入一变，模型/阈值就崩。
2. **阈值靠手调，不是自适应**：`cv2.inRange(hsv, (0, 0, 100), (180, 40, 255))` 这种写法，光照一变，`V`（亮度）通道整体偏移，阈值就不适用了。手调阈值本质上是"把当时的现场条件写死在代码里"。
3. **只测了单一维度**：只测"晴天中午、静止、直道"，没测"逆光、扬尘、夜间、颠簸"。性能下降的边界没人知道，所以看起来"能用"。

> 💡 类比：这就像只用夏天拍的照片训练一个"识别雪"的模型，然后冬天拿去用。不是模型笨，是你没让它见过雪。**感知算法的性能，永远是对某个"场景集合"而言的，脱离场景谈准确率都是耍流氓。**

## 4. "鲁棒性"的工程含义

**鲁棒性（robustness）**：系统在输入发生"没被专门设计过"的变化时，性能下降的幅度。下降得少，就鲁棒；下降得狠，就脆（fragile）。

关键点：鲁棒性不是形容词，而是**可以被量化和验收的指标**。工程上我们这样定义一条可写进验收文档的话：

> "在晴天、阴天、逆光、扬尘、夜间五类工况下，可行驶区域识别召回率均不低于 80%，误报率不超过 10%。"

这句话比"我们的算法很鲁棒"强一百倍，因为它：
- 规定了**工况集合**（测哪些场景）
- 规定了**指标门槛**（召回率、误报率的具体值）
- 可以**复现、可以反驳**（别人拿同样的工况去测，能验真假）

> 💡 类比：说"我这把伞很结实"没法验；说"骨架能抗 8 级风、伞面不漏水、连续开合 500 次不坏"才叫工程指标。鲁棒性就是给"结实"配上一份验收标准。

## 5. 感知组为什么重要：先算一笔时间账

巴哈赛车最高车速约 40~60 km/h，取 50 km/h ≈ **14 m/s**。假设感知到刹车要 0.5 s 反应，刹车距离约 3~5 m。也就是说，**感知系统必须提前十几米发现障碍物**，才有刹车余地。

由此推出两个硬约束：
- 帧率不能低于 **15~20 FPS**（否则两次检测间隔里车已经跑出去 1 m 以上）
- 检测延迟不能超过 **100 ms**（否则再准也来不及）

这两条约束会贯穿后面三讲——**02 讲解决"判得准"，03 讲解决"判得准还得跑得快"**。

### 练习 1：亲手制造一次"颜色特征失效"

用手机在**三种光照**下各拍一张同一段路/同一块地：中午顺光、逆光、树影下。拷到电脑上，跑下面这段代码（Ubuntu 22.04 + Python 3.10 + OpenCV）：

```bash
pip install opencv-python numpy
```

```python
# demo01_hsv_fragile.py
import cv2
import numpy as np

# 把三张照片改好名字放到当前目录
files = ["road_noon.jpg", "road_backlight.jpg", "road_shadow.jpg"]

for f in files:
    img = cv2.imread(f)
    if img is None:
        print(f"[跳过] 读不到 {f}，检查文件是否存在、名字是否一致")
        continue

    hsv = cv2.cvtColor(img, cv2.COLOR_BGR2HSV)

    # 一套"在中午照片上调好"的固定阈值：只保留中高亮度、低饱和度的像素
    low  = np.array([0,   0, 100])
    high = np.array([180, 60, 255])
    mask = cv2.inRange(hsv, low, high)

    ratio = mask.mean() / 255.0   # 被判为"可行驶"的像素占比
    print(f"{f}: 平均亮度 V={hsv[:, :, 2].mean():6.1f}, 被判为可行驶的像素占比 = {ratio:.1%}")
```

> ✅ 你应该看到（类似）：
> ```
> road_noon.jpg:      平均亮度 V= 158.3, 被判为可行驶的像素占比 = 71.4%
> road_backlight.jpg: 平均亮度 V=  61.7, 被判为可行驶的像素占比 =  9.8%
> road_shadow.jpg:    平均亮度 V=  95.2, 被判为可行驶的像素占比 = 33.1%
> ```
> **结论**：同一套阈值，中午能覆盖 70% 的路面，逆光只剩不到 10%。这就是"颜色特征脆"的第一手证据——把它写进你的实验记录里，比任何空谈都有说服力。
> （数字会随你的照片变化，重点看**趋势**：中午判出大片路面 → 逆光/树影下大幅缩水。若你的照片里逆光那张还判出很多区域，说明它还不够逆光，换一张更极端的。）
