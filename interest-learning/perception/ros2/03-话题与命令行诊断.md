## 1. 为什么要学命令行诊断

机器人程序挂掉时，屏幕上往往只有一句 `[ERROR] no data received`。这时候你需要的不是猜，而是**把系统当成一个黑盒，从外面观察数据流**。ROS 2 的命令行工具就是这台"示波器"——不用改一行代码，就能看到话题上有没有数据、多少赫兹、内容长什么样。

> 💡 类比：命令行诊断像医生查房。`node list` 是"病人还在不在病房"，`topic list` 是"身上插了哪几根管子"，`topic info` 是"管子两端分别接着谁"，`topic hz` 是"心跳一分钟跳几次"，`topic echo` 是"抽血化验看指标"。按顺序查，别一上来就开刀（改代码）。

## 2. 四条基本命令

启动实验台：

```bash
# 终端1
ros2 run turtlesim turtlesim_node
```

### 2.1 `ros2 topic list` —— 有哪些频道

```bash
ros2 topic list        # 只列话题名
ros2 topic list -t     # 顺便列出消息类型
ros2 topic list -v     # 更详细（含发布/订阅者数量）
```

> ✅ 你应该看到（`-t` 版本）：
> ```
> /parameter_events [rcl_interfaces/msg/ParameterEvent]
> /rosout [rcl_interfaces/msg/Log]
> /turtle1/cmd_vel [geometry_msgs/msg/Twist]
> /turtle1/pose [turtlesim/msg/Pose]
> ```
> `/rosout` 和 `/parameter_events` 是每个节点自动带的，不用管；`/turtle1/cmd_vel` 是"输入指令"，`/turtle1/pose` 是"当前位姿"。

### 2.2 `ros2 topic info` —— 这条频道两端接着谁

```bash
ros2 topic info /turtle1/cmd_vel
ros2 topic info /turtle1/cmd_vel -v     # 列出具体是哪些节点
```

> ✅ 你应该看到：
> ```
> Type: geometry_msgs/msg/Twist
> Publisher count: 0
> Subscription count: 1
> ```
> **这就是最有价值的一行信息**：订阅者有 1 个（乌龟自己在听），但发布者 0 个——所以乌龟一动不动。等你用 `ros2 topic pub` 发指令，Publisher count 才会变成 1。

### 2.3 `ros2 topic echo` —— 内容对不对

```bash
ros2 topic echo /turtle1/pose          # 持续打印每一帧内容
ros2 topic echo /turtle1/pose --once   # 只看一帧就走
```

> ✅ 你应该看到：
> ```
> x: 5.544444561004639
> y: 5.544444561004639
> theta: 0.0
> linear_velocity: 0.0
> angular_velocity: 0.0
> ---
> ```
> 用鼠标点乌龟窗口里的小乌龟并拖动，`x`/`y` 会实时变化。**看到数字在变，说明数据流是活的。**

### 2.4 `ros2 topic hz` —— 实时频率（FPS）⭐

**试题技术类 1(2) 的答案就是它：`ros2 topic hz <话题名>`。**

```bash
ros2 topic hz /turtle1/pose
```

> ✅ 你应该看到（数值在持续刷新）：
> ```
> average rate: 62.500
> 	min: 0.015s max: 0.017s std dev: 0.00037s window: 62
> average rate: 62.500
> 	min: 0.015s max: 0.017s std dev: 0.00037s window: 62
> ```
> 意思：这个话题每秒发布约 62.5 次。如果换成车上相机的话题，这里打印的就是**相机真实的 FPS**。

**为什么这个方法这么重要？**

对感知组来说，`ros2 topic hz /camera/image_raw` 的输出就是"摄像头到底跑多少帧"的**唯一可信来源**。相机标称 30 FPS，实际可能因为 USB 带宽、曝光时间、驱动问题掉到 12 FPS；你的算法又慢，最终入到神经网络的可能只有 5 FPS——**不去实测，永远不知道瓶颈在哪**。而且比较这两条命令的输出：

```bash
ros2 topic hz /camera/image_raw      # 相机出图的真实 FPS
ros2 topic hz /perception/result     # 你算法出结果的真实 FPS
```

两者差距就是算法消耗的时间。这也是后面"算力优化"那一类题目的实测依据。

**参数小抄：**

| 命令 | 作用 |
|------|------|
| `ros2 topic hz <话题>` | 打印平均发布频率（默认统计最近 1 秒的窗口） |
| `ros2 topic hz <话题> -w 20` | 统计窗口改成 20 帧，适合低频话题更快出结果 |
| `ros2 topic bw <话题>` | 打印**带宽**（MB/s）——图像话题必看，直接决定要不要降分辨率 |
| `ros2 topic delay <话题>` | 打印端到端延迟（需要消息带时间戳） |

> 💡 类比：`ros2 topic hz` 就是给话题量体温——一秒摸几次脉。相机每秒出几帧，一摸便知，比翻相机说明书靠谱一百倍。

> ⚠️ 常见坑：
> 1. **话题没数据时 `hz` 会一直空转**，什么都不打印，不会报错。不打印 = 没数据，不是命令坏了。
> 2. **`hz` 测的是发布频率，不是你的处理速度**。发布者 30 Hz，你的回调每秒只能处理 5 次，`hz` 照样显示 30——想知道自己慢不慢，要看你输出的那条话题的 `hz`。
> 3. `ros2 topic hz` 会真的去订阅这条话题，**会轻微占用一点带宽和 CPU**，长时间挂在图像话题上时要心里有数。

## 3. 看清整张网：`ros2 node list` 与 `rqt_graph`

```bash
ros2 node list      # 系统里现在活着哪些节点
rqt_graph           # 图形化显示"节点 → 话题 → 节点"的连线
```

> ✅ 你应该看到：`ros2 node list` 打印 `/turtlesim`。终端 2 里你如果再开一个 `ros2 topic echo`，`rqt_graph` 里就会出现一个 `_ros2cli_xxxx` 的"临时节点"连在话题上——**说明 echo 命令本身就是个订阅者**。

`rqt_graph` 需要图形界面（WSL 需要 WSLg 或 X Server）。画出来的图里，**椭圆是节点，方框是话题，箭头是数据流向**。车上一出问题，先开 `rqt_graph` 看一眼：该连的线断了没有，一眼就能看出来。

## 4. 四步诊断流程（背下来）

车上"感知没输出"该怎么查？按顺序走，每一步都有明确的判断标准：

| 步骤 | 命令 | 判断标准 | 不对怎么办 |
|------|------|----------|-----------|
| ① 节点在不在 | `ros2 node list` | 相机/感知节点名都在 | 不在 → 节点崩了，查它自己的日志 |
| ② 话题有没有 | `ros2 topic list` + `topic info` | 话题存在，且 Publisher count ≥ 1 | Publisher 为 0 → 上游节点没在发 |
| ③ 频率对不对 | `ros2 topic hz <话题>` | 相机 ≥ 25 Hz，感知 ≥ 10 Hz | 频率太低 → 降分辨率/换算法（算力问题） |
| ④ 内容对不对 | `ros2 topic echo <话题> --once` | 数据合理（图像非全黑、坐标不飞天） | 内容怪 → 算法或标定问题 |

**顺序不能颠倒**：④ 的内容问题往往被 ③ 的低频率掩盖；而 ③ 又必须建立在 ② 有数据之上。跳过前三步直接改代码，是最常见的浪费时间方式。

## 🎯 课后练习（约8分钟）

```bash
# 终端1：启动乌龟
source /opt/ros/humble/setup.bash
ros2 run turtlesim turtlesim_node
```

```bash
# 终端2：完整走一遍四步诊断
source /opt/ros/humble/setup.bash

ros2 node list                       # ① 节点在不在
ros2 topic list -t                   # ② 有哪些话题
ros2 topic info /turtle1/cmd_vel     # ② 谁在发、谁在收（应为 Publisher 0 / Sub 1）

ros2 topic hz /turtle1/pose          # ③ 先看稳定频率，约 62.5 Hz，Ctrl+C 退出

# 再开一个终端3发指令，观察终端2的 hz 有没有变化
ros2 topic pub -r 5 /turtle1/cmd_vel geometry_msgs/msg/Twist "{linear: {x: 2.0}, angular: {z: 1.8}}"

# 终端2继续：
ros2 topic bw /turtle1/pose          # 看看带宽多大
ros2 topic echo /turtle1/pose --once # ④ 内容对不对
```

> ✅ 你应该看到：
> - `ros2 node list` → `/turtlesim`
> - `ros2 topic hz /turtle1/pose` → `average rate: 62.500`（持续刷屏）
> - `ros2 topic info /turtle1/cmd_vel` 在终端3开始发指令后，再用 `-v` 看，Publisher count 变成 1，并列出 `_ros2cli_xxxx`
> - `ros2 topic echo --once` → 打印当前 `x / y / theta`

**挑战**：打开 `rqt_graph`，找到 `_ros2cli_xxxx` 那个临时节点。它就是你的 `echo` 命令——**命令行工具本身也是节点**，这句话理解了，ROS 2 就通了。

## 本讲小结

| 命令 | 用途 | 常见判断 |
|------|------|----------|
| `ros2 node list` | 列出活着的节点 | 该在的节点不在 → 它崩了 |
| `ros2 topic list -t` | 列出话题及类型 | 话题不存在 → 上游没发 |
| `ros2 topic info <话题>` | 看发布/订阅者数量 | Publisher count=0 → 没人发数据 |
| `ros2 topic echo <话题>` | 打印话题内容 | 数据异常 → 算法/硬件问题 |
| **`ros2 topic hz <话题>`** | **打印实时发布频率（FPS）** | **试题 1(2) 答案；掉帧靠它定位** |
| `ros2 topic bw <话题>` | 打印带宽 | 图像话题必看，决定降不降分辨率 |
| `rqt_graph` | 图形化看节点与话题连线 | 该连的线断了没有 |
| 诊断顺序 | 节点 → 话题 → 频率 → 内容 | 顺序不可颠倒 |
