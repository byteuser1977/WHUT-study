## 1. 从一个具体场景说起

车上的摄像头每秒拍 30 张图。感知程序要把这 30 张图拿到手，一路做识别，最后告诉控制程序"往左打 10 度"。

问题是：**摄像头的程序和感知的程序，谁认识谁？**

答案是：谁也不认识谁。摄像头程序只管把图像"喊出去"，谁在听它不关心；感知程序只管"我要图像"，从哪来它也不关心。中间那根线，就是 **Topic**。

## 2. Topic 与 Message

- **Topic（话题）**：一条有名字的数据通道，是数据流的"频道名"。名字通常长这样：`/camera/image_raw`、`/perception/drivable_area`。以 `/` 开头表示绝对路径，避免重名冲突。
- **Message（消息）**：在这条通道上流动的**具体数据包**，而且是有固定格式（类型）的数据包。
- **消息类型**：一个数据结构定义。比如 `std_msgs/msg/String` 里面只有一个字符串字段；图像用 `sensor_msgs/msg/Image`，里面有宽、高、编码格式和一整块像素数据。

> 💡 类比：Topic 是"频道名"，Message 是"这一期节目的内容"，消息类型就是"节目必须按这个格式录制"。你不能在只播语音的频道里塞一段视频——类型对不上，订阅者直接收不到。

| 概念 | 一句话解释 | 巴哈车上的例子 |
|------|-----------|----------------|
| Topic | 有名字的数据通道 | `/camera/image_raw` |
| Message | 通道里流动的单个数据包 | 第 1024 帧图像 |
| 消息类型 | 消息的字段格式定义 | `sensor_msgs/msg/Image` |
| Publisher | 往话题里写数据的一方 | 相机驱动 |
| Subscriber | 从话题里读数据的一方 | 感知节点 |

## 3. 核心：广播电台与收音机（试题 1(1)）

这是本讲最重要的一节，也是试题技术类第 1(1) 题的答案。

**先说结论：**
- **发布者（Publisher）** 像**广播电台**：它把节目（数据）播出去，但它**根本不知道谁在收听**，也不知道有几个人在听。收音机没打开，它照播不误。
- **订阅者（Subscriber）** 像**收音机**：它调到某个频率（话题），就能听到对应节目。它**不需要认识电台**，也不需要给电台打电话申请——只要频率对得上，就能收到。
- **话题（Topic）** 就是那个**频率/频道**：电台和收音机之间唯一的约定。电台不需要知道有哪些收音机，收音机也不需要知道电台在哪，双方只约定了"我们都在 98.5 兆赫上说话"。
- **消息（Message）** 是**这一期节目的内容**：改了节目内容不影响频率，换了电台主播也不影响收音机。

**再补三个关键性质，答面试题时说出来就是加分项：**

1. **单向（one-way）**：数据只从发布者流向订阅者，不回流。电台不会知道你把音量调到了几。感知节点要"回话"给控制节点？那是另开一条话题，或者用第04讲的服务（Service）。
2. **解耦（decoupled）**：发布者和订阅者互不知道对方的存在，也不知道对方的数量。**开或者关，对对方没有任何影响**——这就是为什么"相机节点先跑，感知节点后起"完全没问题。
3. **多对多（many-to-many）**：一个话题可以有多个发布者（多个电台挤在一个频率上，会互相干扰，一般避免），也可以有任意多个订阅者（一千台收音机听同一个电台，电台毫无压力）。这正是感知组最需要的：感知结果同时给控制、给仪表盘显示、给日志记录，而感知节点一个字都不用改。

> 💡 类比加强版：发布者像"群里发消息的人"，订阅者是"群里所有人"。发消息的人不需要挨个私聊，也不需要知道群里有多少人；新同学进群也不会打扰到发消息的人。Topic 就是这个"群名"。

> ⚠️ 常见坑一：**"发了就没人收"不是错误**。话题上只有发布者、没有订阅者时，数据直接丢掉，ROS 2 不会报错也不会缓存等你。所以"我的程序收不到数据"，第一件事不是怀疑代码，而是去查话题上到底有没有发布者（第03讲）。
> ⚠️ 常见坑二：**订阅者后启动，收不到之前的数据**（除非专门配置 QoS 做持久化）。收音机打开之前播的节目，就是错过了。
> ⚠️ 常见坑三：**话题名写错一个字母，就等于调错频率**。`/camera/image_raw` 和 `/camera/image/raw` 在 ROS 2 眼里是两个完全无关的频道。

## 4. 亲手发一条消息：`ros2 topic pub`

不用写任何代码，ROS 2 自带一个"人工电台"命令，可以手动往话题里发消息。

命令格式（后面讲诊断时还会用到）：

```bash
ros2 topic pub <话题名> <消息类型> "<消息内容>" [--once | -r 频率]
```

实战——让仿真小乌龟动起来：

```bash
# 终端1：启动小乌龟
ros2 run turtlesim turtlesim_node

# 终端2：先看看有哪些话题、它们是什么类型
ros2 topic list -t

# 手动发一次速度指令，让乌龟走一小步
ros2 topic pub --once /turtle1/cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 2.0, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 1.8}}"

# 以 10 Hz 持续发：乌龟会一直画圆（Ctrl+C 停）
ros2 topic pub -r 10 /turtle1/cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 2.0}, angular: {z: 1.8}}"
```

> ✅ 你应该看到：
> 终端 2 每秒打印 10 行左右的
> `publishing #12: geometry_msgs.msg.Twist(linear=..., angular=...)`，
> 同时乌龟窗口里的小乌龟开始沿一个圆圈跑。`--once` 那次则只是轻轻挪动一下。

这段命令里 `Twist` 是"速度"消息类型：`linear` 是线速度（米/秒），`angular` 是角速度（弧度/秒）。车上的底盘指令、云台角度，本质上都是这类消息。

## 🎯 课后练习（约8分钟）

```bash
# 终端1
source /opt/ros/humble/setup.bash
ros2 run turtlesim turtlesim_node
```

```bash
# 终端2
source /opt/ros/humble/setup.bash
ros2 topic list          # 看系统里现在有哪些频道
ros2 topic list -t       # 顺便看每个频道的消息类型

# 猜一猜：哪个话题是小乌龟的位置？
ros2 topic pub --once /turtle1/cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 2.0, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 1.8}}"

# 持续发 10 Hz，让它画圆
ros2 topic pub -r 10 /turtle1/cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 2.0}, angular: {z: 1.8}}"
```

> ✅ 你应该看到：
> `ros2 topic list` 输出类似 `/parameter_events`、`/rosout`、`/turtle1/cmd_vel`、`/turtle1/pose`；
> `-t` 版本会在后面跟上类型，如 `/turtle1/cmd_vel [geometry_msgs/msg/Twist]`。
> 持续发指令后，乌龟在窗口里转圈，直到你 `Ctrl+C` 停掉发布。

**思考题**：把终端 1 的乌龟关掉，但让终端 2 继续发消息。会报错吗？——不会。发布者不需要订阅者，消息发出去没人接而已。这就是"解耦"。

## 本讲小结

| 概念 | 要点 |
|------|------|
| Topic（话题） | 有名字的数据通道，相当于收音机的"频率" |
| Message（消息） | 流动的数据包，有固定的消息类型 |
| Publisher（发布者） | 广播电台：只发不收，不知道谁在听、有几个人听 |
| Subscriber（订阅者） | 收音机：只收不发，不认识电台，频率对上就收到 |
| 通信特性 | 单向、解耦（互不知晓）、多对多（一个发多个收） |
| 关键命令 | `ros2 topic list -t`、`ros2 topic pub <话题> <类型> "<内容>"` `--once` / `-r 10` |
| 答试题 1(1) | 电台发、收音机收、频率是话题、节目是消息；发布者不知谁在听，订阅者不需申请 |
