# 第04讲：服务、参数与动作（正文约9分钟 + 练习约7分钟）

## 你将学到
- Service（服务）的"请求-响应"和 Topic 的单向广播差在哪
- Parameter（参数）怎么在不改代码的前提下调节点
- Action（动作）为什么专治"要跑很久、还要看进度"的任务
- 一张"三者选型对照表"，遇到需求直接对号入座

---

## 1. Topic 解决不了所有问题

上一讲说，Topic 是广播电台——单向、多对多、发完不管。这套模型对"持续不断的数据流"简直完美：图像、位姿、速度指令，都是这种。

但下面这些需求，Topic 就不合适了：

- 我想让感知节点**清空一次缓存**，然后告诉我"清完了"。→ 需要一问一答，而且我要知道对方收到没有。
- 我想把相机的曝光时间从 10 ms 改成 20 ms。→ 这只是改一个设置值，不需要另开一条话题专门发它。
- 我想让车**沿这条路走 30 米并掉头**，过程中还要看到"已完成 40%"。→ 这是个**长任务**，有过程、有结果、还可能中途取消。

对应的答案就是：**Service、Parameter、Action**。

## 2. Service（服务）：打电话，一问一答

- **Service（服务）**：一种**请求-响应（request-response）**式的通信。客户端（Client）发一个请求，服务端（Server）处理完**必须回一个响应**。
- 关键词是"同步"和"一次性"：**它不适合传持续的数据流**，只适合"做一件事、给个结果"。

> 💡 类比：Topic 像广播电台（不知道谁在听、只管播），Service 像**打客服电话**——你拨号（请求），客服接起（服务端在监听），你说事，他处理完明确答复你（响应）。**如果客服不在线，你这通电话直接失败**——这和电台完全不同，电台不播你也没办法。

```bash
# 看看系统里有哪些服务（需先启动 turtlesim）
ros2 service list
ros2 service type /clear             # 看这个服务请求/响应的类型
ros2 service call /clear std_srvs/srv/Empty      # 清空画面上的轨迹
```

> ✅ 你应该看到：
> ```
> /clear
> /kill
> /reset
> /spawn
> /turtle1/set_pen
> /turtle1/teleport_absolute
> /turtle1/teleport_relative
> /turtlesim/get_parameters
> ...
> ```
> 以及 `ros2 service call /clear ...` 之后打印
> `requester: making request: std_srvs.srv.Empty_Request()` 和 `response: std_srvs.srv.Empty_Response()`，**乌龟窗口里画出的轨迹立刻被擦干净**。

| 对比项 | Topic | Service |
|--------|-------|---------|
| 方向 | 单向（发→收） | 双向（请求 ↔ 响应） |
| 有没有回执 | 没有，发完就完 | 有，必须回响应 |
| 数量关系 | 多对多 | 通常客户端/服务端各 1（服务端可被多个客户端调用） |
| 适合 | 持续数据流（图像、位姿） | 一次性命令（开关、清空、查询） |
| 没人在听时 | 数据丢弃，不报错 | 服务端不存在 → 调用直接失败 |
| 关键命令 | `ros2 topic ...` | `ros2 service list / type / call` |

> ⚠️ 常见坑：**别拿 Service 传图像/持续数据流**。Service 的请求-响应模型带握手开销，频率高时会成为瓶颈；而且它是阻塞式的，服务端忙的时候客户端就等着。**持续数据一律用 Topic。**

## 3. Parameter（参数）：不改代码就调节点

- **Parameter（参数）**：节点自身暴露出来的**配置项**，有名字、有类型、有当前值。你能在节点运行期间读它、改它，**改了立刻生效，不用重新编译、不用重启程序**。

这解决一个极其实用的问题：调 PID 三个系数、调阈值、调曝光，如果每次都要改代码再重编译，一天时间就没了。

```bash
ros2 param list                                    # 列出所有节点的参数
ros2 param get /turtlesim background_g             # 读某个参数当前值
ros2 param set /turtlesim background_g 200         # 改它
ros2 param dump /turtlesim                         # 把全部参数导出成 YAML
```

> ✅ 你应该看到：
> - `ros2 param list` 输出 `/turtlesim: background_b, background_g, background_r, use_sim_time`
> - `ros2 param get /turtlesim background_g` → `Integer value is: 69`
> - `ros2 param set /turtlesim background_g 200` → `Set parameter successful`，**乌龟窗口背景的绿色分量明显变亮**（注意：部分参数需要重启节点才完全生效）

> 💡 类比：Parameter 像**空调遥控器**。空调（节点）一直在运行，你按一下遥控器改温度（参数），它立刻执行——你不需要把空调拆了重新生产一台（重编译）。`ros2 param dump` 就是把当前遥控器上的所有设置抄下来，下次照着设一遍。

> ⚠️ 常见坑：**`ros2 param get` 的名字是"节点名 + 参数名"**，不是话题名。节点名忘了带 `/` 或者写错，会报 `Node not found`。另外 `ros2 param set` 的参数**默认不跨节点重启保存**，想持久化要用 `--params-file` 在启动时加载（第05讲的 launch 文件里会用到）。

## 4. Action（动作）：长任务的正确做法

- **Action（动作）**：一种**三合一**的通信机制——发送一个目标（goal）、**过程中持续反馈（feedback）**、最后给一个结果（result），并且**支持中途取消（cancel）**。

它是为"要跑很久、你还想看进度"的任务设计的：

| 场景 | 用 Service 会怎样 | 用 Action 的体验 |
|------|------------------|------------------|
| 转向 90° | 请求发出去，界面卡住等 3 秒 | 每秒收到"已转 40% / 70%" |
| 走完一条 30 m 路径 | 界面冻结 20 秒无从判断卡没卡 | 实时进度条，随时能取消 |
| 相机自动对焦 | 只能等到结束 | 看得到每一步 |

```bash
ros2 action list                          # 有哪些动作
ros2 action list -t                       # 带类型
ros2 action send_goal /turtle1/rotate_absolute \
  turtlesim/action/RotateAbsolute "{theta: 1.57}" --feedback
```

> ✅ 你应该看到：
> ```
> Waiting for an action server to become available...
> Sending goal:
>      theta: 1.57
> Goal accepted.
> Feedback:
>     remaining: 1.5750306844711304
> Feedback:
>     remaining: 0.9708412289619446
> Feedback:
>     remaining: 0.0
> Result:
>     delta: 0.004969315528869629
> ```
> **连续多条 Feedback 就是"进度条"，最后一条 Result 是"完成"**。乌龟在窗口里平滑地转到了约 90°。

> 💡 类比：Action 像**点外卖**。下单（goal）之后，你不用干等，App 会一路推送"商家接单 → 骑手取餐 → 距你 500 米"（feedback），最终"已送达"（result）；路上你还能点"取消订单"（cancel）。如果只是问"你们几点关门"这种一句话的事——那是 Service。

## 5. 三者选型对照表（背下来）

| 对比项 | Topic | Service | Parameter | Action |
|--------|-------|---------|-----------|--------|
| 通信模型 | 单向广播 | 请求-响应 | 读/写一个配置值 | 目标 + 反馈 + 结果 |
| 有反馈吗 | 无 | 只有一个最终响应 | 无 | **有，过程持续反馈** |
| 能取消吗 | 不适用 | 不能 | 不适用 | **能** |
| 阻塞吗 | 不阻塞 | 阻塞等待响应 | 立即返回 | 不阻塞，可并行等 |
| 典型时长 | 持续不断 | 毫秒~秒级 | 瞬间 | 秒~分钟级 |
| 车上例子 | 图像、位姿、速度指令 | 清空缓存、切换模式、查询状态 | 曝光时间、阈值、PID 系数 | 走完路径、掉头、自动对焦 |
| 常用命令 | `ros2 topic ...` | `ros2 service ...` | `ros2 param ...` | `ros2 action ...` |

**一句话选择法**：源源不断的数据 → Topic；做一件事要个结果 → Service；边做边报进度或可能取消 → Action；只是改个设置值 → Parameter。

## 🎯 课后练习（约7分钟）

```bash
# 终端1
source /opt/ros/humble/setup.bash
ros2 run turtlesim turtlesim_node
```

```bash
# 终端2
source /opt/ros/humble/setup.bash

# ① Service：先画几笔，再一键清屏
ros2 topic pub -r 5 /turtle1/cmd_vel geometry_msgs/msg/Twist "{linear: {x: 2.0}, angular: {z: 1.8}}"
# Ctrl+C 停止后：
ros2 service list
ros2 service call /clear std_srvs/srv/Empty

# ② Service：再生成一只乌龟（注意 spawn 的请求里要带名字）
ros2 service call /spawn turtlesim/srv/Spawn "{x: 2.0, y: 2.0, theta: 0.0, name: 'turtle2'}"
ros2 topic list        # 应能看到 /turtle2/cmd_vel 等新话题

# ③ Parameter：读一个、改一个
ros2 param list
ros2 param get /turtlesim background_b
ros2 param set /turtlesim background_b 255

# ④ Action：带反馈地转 90°
ros2 action list -t
ros2 action send_goal /turtle1/rotate_absolute turtlesim/action/RotateAbsolute "{theta: 1.57}" --feedback
```

> ✅ 你应该看到：
> - `spawn` 返回 `response: turtlesim.srv.Spawn_Response(name='turtle2')`，窗口里多出一只新乌龟
> - `param set` 返回 `Set parameter successful`
> - `send_goal ... --feedback` 连续打印多行 `Feedback: remaining: x.xx`，最后打印 `Result: delta: x.xx`

**自测**：把"让乌龟转 90°"改用 Service 的思路实现会有什么体验问题？（答：界面上完全看不到中间进度，也无法中途取消，3 秒里你只能干等——这正是 Action 存在的意义。）

## 本讲小结

| 概念 | 要点 |
|------|------|
| Service | 请求-响应，一问一答，有回执；不适合持续数据流 |
| Parameter | 节点暴露的配置项，运行时读/写，改完即时生效，无需重编译 |
| Action | 长任务专用：目标 + 持续反馈 + 最终结果 + 可取消 |
| Topic vs Service | 单向广播无回执 vs 双向请求有响应 |
| Service vs Action | 短任务一次性 vs 长任务带进度可取消 |
| 选型口诀 | 数据流用 Topic，要结果用 Service，要进度用 Action，改设置用 Parameter |
| 命令家族 | `ros2 topic / service / param / action` 各自有 list、info、call/set/send_goal |
