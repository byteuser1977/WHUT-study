## 你将学到
- 把"我想让车看懂赛道"拆成一张能逐条打勾的检查清单

## 1. 从需求到落地：先写功能清单

写代码之前，先用一张表把"要什么"讲清楚。凡是说不清"输入是什么、输出是什么、多快、怎么算成功"的需求，都不算需求。

| 功能 | 输入 | 输出 | 频率 | 验收标准 |
|------|------|------|------|---------|
| 可行驶区域识别 | 前视相机图像 640×480 | 掩膜图 + 面积占比 | ≥ 10 FPS | 白天正常路面掩膜覆盖率 > 90% |
| 障碍物提示 | 同一帧图像 | 目标框 + 最近距离等级 | ≥ 10 FPS | 3 米内高锥桶不漏报 |
| 车道边界 | 图像下半部分 ROI | 左/右边界点 | ≥ 15 FPS | 直道抖动 < 10 像素 |

> 💡 类比：飞行员起飞前的检查单。再熟练的机长也不会"凭感觉"起飞——清单的作用不是教他开飞机，而是**保证在紧张、疲惫、赶时间的时候也不会漏掉关键项**。感知上车前，你也需要这样一张单子。

## 2. 环境固定：让"在我电脑上是好的"不再出现

- 写清版本：Ubuntu 22.04 + ROS 2 Humble + Python 3.10 + OpenCV 4.5.4
- 依赖落成文件：`requirements.txt`（pip 库）+ `install.sh`（记录每条 apt 包）
- 换机器前先在干净环境里按文档装一遍，验证能跑通
- 有条件就上 Docker：把"环境"整个装进一个镜像，谁跑都一样
- 记录硬件：相机型号、分辨率、帧率、安装角度（安装角度变了，ROI 全废）

> ⚠️ 常见坑：`pip install opencv-python` 和 `apt install python3-opencv` 是两套不同的包，混用会出现"两个 OpenCV、GUI 崩、cv_bridge 冲突"的玄学问题。**项目里只留一套，并写进 README。**

## 3. 日志与可复现：出事能回放

| 手段 | 命令 / 做法 | 解决什么问题 |
|------|------------|-------------|
| 录包 | `ros2 bag record /camera/image_raw /perception/mask` | 现场数据带回实验室反复调试，不用一遍遍开车 |
| 回放 | `ros2 bag play <包名>` | 同一段数据对比新旧算法，公平可比 |
| 日志级别 | 关键判断处打 `INFO`，可疑处打 `DEBUG` | 事后能看出"当时为什么这么判" |
| 参数入库 | 把本次参数打印或写入日志 | 结果异常时能确认是算法问题还是参数问题 |
| 实验记录 | 一张表：日期 / 改了什么 / 结果 / 结论 | 避免重复踩同一个坑 |

实验记录表示例（手写也行）：

| 日期 | 改动 | 结果 | 结论 |
|------|------|------|------|
| 9-18 | 阈值 130 → 145 | 下午强光下误检减少 | 保留，写进默认参数 |
| 9-19 | 分辨率降到 320×240 | FPS 22 → 45，30 米外锥桶漏检 | 只在低速工况启用 |

## 4. 仿真先跑 + 单元测试

**仿真先跑**：能在仿真或 bag 回放里发现问题，就不要上真车。车上一分钟，实验室十分钟；车上撞一次，可能是一周。

**单元测试**：给算法喂固定输入，断言输出在合理范围。感知代码也能测，而且非常值得测。

```python
# test_perception.py  —— 运行：python3 -m pytest test_perception.py -v
import numpy as np
from perception import segment   # 只测这一个函数，不碰摄像头

def test_segment_full_road_mask():
    """整幅亮图的掩膜面积应该接近全图，不能是空的"""
    img = np.full((240, 320, 3), 200, dtype=np.uint8)
    mask = segment(img)
    assert mask.shape == (240, 320)
    assert mask.mean() > 0.8, "亮路面应该被判为可行驶"

def test_segment_all_black_no_crash():
    """全黑图（镜头被遮住）不能崩，应返回全 0 掩膜"""
    mask = segment(np.zeros((240, 320, 3), dtype=np.uint8))
    assert mask.sum() == 0

def test_segment_returns_correct_shape():
    """返回尺寸必须和输入一致，否则坐标平移会错"""
    mask = segment(np.random.randint(0, 255, (240, 320, 3), dtype=np.uint8))
    assert mask.shape == (240, 320)
```

> ✅ 你应该看到（类似）：`3 passed in 0.4s`。全黑图、超亮图这两个用例最能暴露隐藏 Bug——**镜头被泥水糊住就是全黑图。**

> ⚠️ 常见坑：只在"正常光照的漂亮图片"上调试。上赛道第一天，镜头沾水、逆光、全黑，程序直接崩，车上没人能救。

## 5. 参数外置：不要把数字写死在代码里

| 写法 | 后果 |
|------|------|
| `if gray > 145:` 写死在代码里 | 换个光照就要改代码、重新构建、重新上车 |
| `self.declare_parameter('thresh', 145)` | 命令行改 `--ros-args -p thresh:=160`，10 秒调好 |

```python
self.declare_parameter('thresh', 145)          # 声明参数
self.declare_parameter('roi_top', 0.5)         # ROI 起始比例
thresh = self.get_parameter('thresh').value    # 取用
roi_top = int(self.get_parameter('roi_top').value * h)
```

要外置的典型参数：阈值、ROI 上下边界、分辨率与帧率、相机 device_id、模型路径、日志级别、串口名。

> 💡 类比：空调遥控器。温度写死在机器内部，你得拆机才能调；有遥控器，坐在沙发上就能改。**参数外置 = 给算法装一个遥控器。**

## 6. 失败降级：一定会出问题，区别只是你准备好了没

按优先级**逐级往下降**，而不是一崩到底：

1. 正常：全功能，全分辨率、全帧率
2. 降级一：降分辨率 / 抽帧，保住基本识别
3. 降级二：只保留最基础功能（例如只报"前方有障碍"，不做分类）
4. 降级三：只上报心跳与警告，交给人接管或安全减速停车

配套要做的两件事：

- **看门狗（watchdog）**：话题超过 N 秒没有新消息，就判定"感知挂了"，主动报警。别让上层以为"没有障碍物"。
- **输入校验**：每帧先检查 `frame is not None and frame.shape == (480, 640, 3)`，不合法就跳过并计数，计数超限报警。

> ⚠️ 最危险的失败模式不是崩溃，而是**静默地给错答案**：摄像头断线了，程序继续发上一帧的掩膜，车以为路是通的。

## 7. 现场调试习惯

| 习惯 | 为什么 |
|------|--------|
| **先看日志，后改代码** | 80% 的"算法坏了"其实是"话题名变了/节点没起/相机没接" |
| **一次只改一处** | 改三处同时测，帧率变了你也说不清是谁的功劳（呼应第 01、03 讲） |
| **保留回滚点** | 上车前先 `git commit` 或打 tag，改坏了 10 秒回滚 |
| **车上只改参数，不改代码** | 车上环境紧张又危险；代码改动回实验室做，车上用 `-p` 调参数 |
| **车下 dry run** | 先用 bag 回放或静态图片跑一遍，再上真车 |

排查顺序固定成四步（和你第 03 讲学的诊断流程一致）：

```bash
ros2 node list                     # ① 节点在不在
ros2 topic list                    # ② 话题有没有
ros2 topic hz /camera/image_raw    # ③ 频率对不对（预期 30 Hz 左右）
ros2 topic echo /perception/mask --once   # ④ 内容对不对
```

## 🎯 课后练习（约10分钟）

给"可行驶区域识别"这个功能做一次体检，把本讲的清单落地成文件。

```bash
mkdir -p ~/perception-checklist && cd ~/perception-checklist

# 1. 建一张上线前检查单（勾选式）
cat > checklist.md <<'EOF'
# 感知节点上线前检查单
- [ ] 环境：README 里的依赖在一台干净机器上装过并跑通
- [ ] 参数：所有阈值/分辨率/ROI 已外置，能用 -p 修改
- [ ] 话题：节点名、话题名与上层约定一致
- [ ] 频率：ros2 topic hz 达到预期（≥10 FPS）
- [ ] 异常：拔掉摄像头不崩，且有告警日志
- [ ] 资源：CPU/内存占用在车机可承受范围内
- [ ] 回滚点：上车前的代码已 commit，参数已备份
- [ ] 数据：本次现场已 ros2 bag record，可回放复现
EOF

# 2. 写三个单元测试（对应第 4 节的例子）
cat > test_utils.py <<'EOF'
import numpy as np

def to_gray(img):
    """BGR -> 灰度，用加权平均，不含 OpenCV 依赖"""
    return (0.114 * img[:, :, 0] + 0.587 * img[:, :, 1] + 0.299 * img[:, :, 2]).astype(np.uint8)

def test_white_image_is_255():
    img = np.full((10, 10, 3), 255, dtype=np.uint8)
    assert to_gray(img).mean() == 255

def test_black_image_is_0():
    img = np.zeros((10, 10, 3), dtype=np.uint8)
    assert to_gray(img).sum() == 0

def test_shape_preserved():
    img = np.random.randint(0, 255, (240, 320, 3), dtype=np.uint8)
    assert to_gray(img).shape == (240, 320)
EOF

# 3. 跑测试（没装 pytest 就用 python3 -m pytest 会提示，可先 pip install pytest）
python3 -m pytest test_utils.py -v
```

> ✅ 你应该看到（类似）：
> ```
> test_utils.py::test_white_image_is_255 PASSED
> test_utils.py::test_black_image_is_0 PASSED
> test_utils.py::test_shape_preserved PASSED
> ============================== 3 passed in 0.05s ==============================
> ```

进阶任务：故意把 `to_gray` 的返回改成 `.astype(np.float32)`，再跑一次测试，观察哪个用例会挂——这就是"单元测试挡住低级错误"的实际体验。

## 本讲小结

| 概念 | 要点 |
|------|------|
| 功能清单 | 每条需求都要有输入/输出/频率/验收标准，说不清就不算需求 |
| 环境固定 | 版本写进 README，依赖落成 requirements.txt + install.sh，最好上 Docker |
| 日志与可复现 | ros2 bag 录制回放、日志分级、参数入库、实验记录表 |
| 仿真与测试 | 能仿真别上真车；喂边界输入（全黑/超亮）写单元测试 |
| 参数外置 | 阈值/ROI/分辨率用 ROS 2 参数，车上 10 秒调好 |
| 失败降级 | 四级降级 + 看门狗 + 输入校验；最怕"静默给错答案" |
| 现场调试 | 先看日志后改代码、一次只改一处、留回滚点、车上只调参数 |
| 排查四步 | node list → topic list → topic hz → topic echo |
