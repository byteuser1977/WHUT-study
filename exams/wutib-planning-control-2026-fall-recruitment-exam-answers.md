## 题 01 　开环 / 闭环速度控制

### 1. 哪个是闭环、哪个是开环？哪种更适合比赛？

- **方案一（上图）是开环控制**：期望速度直接经下位机、电机输出实际速度，输出端没有反馈回路，控制器不关心"实际转到了多少"。
- **方案二（下图）是闭环控制**：实际速度被引回控制器输入端与期望速度比较，用偏差驱动控制器。

**智能巴哈比赛环境更适合闭环控制**，理由：

1. 比赛场地干扰多——草地/沙地/泥地摩擦系数不同，电池电压下降导致电机出力衰减，载荷变化都会让"同样的指令"产生"不同的实际速度"。
2. 开环只能"盲发指令"，无法补偿这些干扰；闭环靠速度反馈实时纠偏，鲁棒性强。
3. 赛规对速度、轨迹有要求（如 A3 跟随路径），只有闭环才能保证实际输出贴近期望。

### 2. 哪一项期望速度与实际速度的拟合度更高？

**方案二（闭环）拟合度更高。**

原因：闭环引入反馈，任何导致实际速度偏离期望的因素（负载变化、电压下降、地面阻力）都会产生偏差信号，控制器据此调整输出，持续把实际速度"拉回"期望值；开环没有这一修正机制，偏差会原样保留甚至累积。

### 3. 强化学习与闭环控制的联系

两者结构高度同构——都是"观察 → 决策 → 执行 → 获得反馈"的循环：

| 环节 | 闭环控制 | 强化学习 |
|---|---|---|
| 状态获取 | 传感器测量 | 环境观察 observation |
| 反馈信号 | 偏差 e = 期望 − 实际 | 奖励 r |
| 决策 | 控制律（PID/Stanley） | 策略 π(a\|s) |
| 执行 | 执行器动作 | 环境 step |
| 目标 | 最小化跟踪误差 | 最大化累积奖励 |

**联系**：
- 强化学习可视为"用数据学习替代人工设计控制律"的闭环——控制律参数不再靠人调，而是通过与环境交互试错优化出来。
- 强化学习的"探索-利用"权衡本质是闭环中"抗扰动 vs 平顺性"权衡的数据化版本。
- 工程上两者常结合：**RL 学习控制律/参数，经典闭环控制负责安全边界与可解释性**（如 RL 输出转角，外层再套限幅和失稳保护）。

**区别**：闭环控制律由人工建模设计、可解释、易验证；强化学习适合高维非线性、难以建模的场景（四足步态、机械臂抓取），但样本效率低、安全性难保证。

## 题 02 　技术基础

### 1. ROS 2 部署环境与术语

**ROS 2 部署在 Linux 系统中**，官方支持 Ubuntu（本团队使用 22.04 LTS），也支持 Windows/macOS/嵌入式平台（如 ROS 2 Galactic+ 对树莓派），但机器人开发的事实标准是 Ubuntu。

| 术语 | 含义 |
|---|---|
| 节点 Node | 独立运行的程序单元，每个节点负责一件事（如激光雷达驱动、路径跟踪） |
| 订阅 Subscribe | 从话题接收消息的动作 |
| 发布 Publish | 向话题发送消息的动作 |
| 时间戳 Timestamp | 消息携带的产生时间，用于多传感器数据时间对齐与延迟检测 |
| 消息 Message | 话题中传输的数据结构（如 Twist、PoseStamped），由 `.msg` 文件定义 |
| 定时器 Timer | 按固定周期触发回调，用于周期性任务（如 100Hz 控制循环） |
| 生命周期节点 Lifecycle | 具有可管理状态机的节点（Unconfigured→Inactive→Active→Finalized），可统一启停、故障恢复 |
| 话题 Topic | 节点间异步单向通信的命名通道，发布/订阅模型 |
| 回调 Callback | 消息到达或定时器到时被调用的处理函数，由执行器在对应线程调度执行 |

### 2. SSH 连接与网线直连操作流程

**SSH（Secure Shell）**：加密的远程终端协议，在不安全网络上建立安全通道，默认端口 22。用途：从笔记本远程登录车载电脑执行命令、传文件（scp/rsync）、转发图形界面，实现"代码在车上跑、人在车边改"。

**两台电脑一根网线直连：**

1. 网线物理连接两台电脑的网口（需交叉线或支持 Auto-MDIX 的网口）。
2. 手动配置同网段 IP（自动 DHCP 在直连下无服务器，会失败）：
   ```bash
   # 电脑 A
   sudo ip addr add 192.168.1.1/24 dev eth0
   # 电脑 B
   sudo ip addr add 192.168.1.2/24 dev eth0
   ```
3. 验证连通：`ping 192.168.1.2`
4. 放行 SSH：确保防火墙允许 22 端口；目标机装好并启动 sshd。
5. 登录：`ssh user@192.168.1.2`，首次连接确认指纹，输入密码（或配密钥免密）。
6. 传文件：`scp ./code.py user@192.168.1.2:~/` 或 `rsync -av ./code/ user@192.168.1.2:~/code/`。

### 3. 双系统与虚拟机的区别与适用条件

| 对比项 | 双系统 | 虚拟机 |
|---|---|---|
| 原理 | 物理机装多个 OS，启动时选择 | 宿主机内运行一个模拟的计算机 |
| 性能 | 原生性能，无损耗 | CPU/内存/IO 有虚拟化开销，GPU 加速受限 |
| 硬件访问 | 直接访问全部硬件 | 部分受限（USB 直通需配置、GPU 弱） |
| 切换 | 重启切换，同一时刻只跑一个 | 随时切换、可与 Windows 并行 |
| 磁盘 | 需要独立分区（安装有分区风险） | 一个镜像文件即可，删除即卸载 |
| 隔离性 | 差，系统间共享硬件 | 好，可快照、可克隆 |

**适用条件**：
- **虚拟机**：学习 Linux、跑轻量开发、需要 Linux 与 Windows 资料并用、怕弄坏主系统——快照可随时回滚。
- **双系统**：需要完整性能和全部硬件访问——**传感器驱动（USB 摄像头、LiDAR）、实车部署、实时性要求高的场景必须用它**。

### 4. Git 与工作区

**Git**：分布式版本控制系统，记录文件每次变更的历史，支持回滚、分支、多人合并，本地即有完整仓库（离线可用）。

| 区域名称 | 作用 |
|---|---|
| 工作区 Working Directory | 你直接编辑的文件所在目录，改动尚未被记录 |
| 暂存区 Staging Area（index） | `git add` 后改动进入这里，构成下一次提交的快照 |
| 仓库 Repository（.git） | `git commit` 后快照永久存入历史，可回溯任意版本 |
| 远程仓库 Remote | 托管在 GitHub/Gitee 上的共享副本，`git push/pull` 与之同步 |

### 5. GitHub 与 Git 的区别、团队是否需要

**区别**：

| | Git | GitHub |
|---|---|---|
| 本质 | 本地运行的版本控制**工具** | 托管 Git 仓库的**云平台** |
| 网络 | 不需要 | 需要 |
| 核心功能 | 版本、分支、合并、历史 | 额外提供 PR/MR Review、Issue、Actions CI、权限管理 |

**团队需要，理由**：
1. **代码共享与备份**：仓库集中，不依赖 U 盘拷贝，单一事实来源。
2. **协作流程**：分支 + Pull Request 实现"写代码 → 评审 → 合并"，避免互相覆盖。
3. **历史可追溯**：谁改了什么、为什么改一目了然，责任到人。
4. **CI/CD**：GitHub Actions 可在推送时自动编译测试，防止把编译不过的代码带进主干。

## 题 03 　带阻尼 Stanley 控制器

### 1. 对 Stanley 的认识

**定位**：Stanley 是经典的**几何类横向路径跟踪算法**（斯坦福大学为无人驾驶挑战赛提出），适配前轮转向车辆，核心是"航向修正 + 横向修正"的复合控制。

**核心逻辑**：
- 同时修正**航向偏差** θ_e（车头朝向与路径切向的差异）与**横向偏差** e（前轴到路径的垂距），让车既对齐方向又贴合位置。
- 横向修正项用 `arctan(k_e·e / v)`：低速时横向增益大、纠偏快；高速时增益自动变小、保证平顺稳定——天然具备速度自适应。

**本代码的工程改进**（相对教科书 Stanley）：
1. **低速软化** `k_s`：`v_eff = |v| + k_s`，防止 v→0 时分母为零与增益爆炸。
2. **阻尼项** `k_d(r − r_ref)`：以路径曲率对应的期望横摆率 r_ref = v·κ 为基准，对横摆角速度偏差施加阻尼，抑制大曲率/高速下的横摆振荡，提升平顺性。
3. **角度归一化 _wrap**：把航向差折叠回 [−π, π]，避免 ±360° 跳变导致转向反打。
4. **转角限幅**：clip 到 ±δ_max（40°），保证物理可行、不超出机械行程。

**优劣势**：结构直观、计算量极小（一次最近邻 + 几个三角函数），非常适合嵌入式实时控制；但忽略轮胎侧偏等动力学特性，高速/大曲率下跟踪精度有限——这是它需要阻尼项，也是极限工况下不如 MPC 的地方。

### 2. 数学公式

**① 最近路径点搜索**
$$idx = \arg\min_i \left[(x_i - x)^2 + (y_i - y)^2\right]$$

**② 角度归一化**
$$\text{Wrap}(\alpha) = (\alpha + \pi) \bmod (2\pi) - \pi$$

**③ 航向误差**
$$\theta_e = \text{Wrap}\left(\theta_{\text{path},idx} - \psi\right)$$
其中 ψ 为车辆航向角 yaw。

**④ 横向误差**（前轴到路径垂距，左正右负）
$$e = -(x_{idx} - x)\sin\psi + (y_{idx} - y)\cos\psi$$

**⑤ 低速软化后的有效速度**
$$v_{\text{eff}} = |v| + k_s$$

**⑥ Stanley 主项**
$$\delta_{st} = \theta_e + \arctan\!\left(\frac{k_e \cdot e}{v_{\text{eff}}}\right)$$

**⑦ 阻尼项修正**（r 为实际横摆角速度，κ 为路径曲率）
$$r_{\text{ref}} = v \cdot \kappa_{idx}$$
$$\delta = \delta_{st} - k_d\,(r - r_{\text{ref}})$$

**⑧ 转角限幅**
$$\delta_{\text{final}} = \text{clip}\left(\delta,\ -\delta_{\max},\ \delta_{\max}\right),\quad \delta_{\max} = 40°$$

**参数（默认值）**：k_e = 0.6（横向误差增益）、k_s = 1.0 m/s（低速软化）、k_d = 0.10 s（阻尼增益）、δ_max = 40°。

## 题 04 　系统架构与规控

### 1. Frenet 坐标系及其作用

**定义**：Frenet 坐标系是**沿参考路径建立的局部坐标系**（由德国数学家 Georg Frenet 命名），用两个量描述位置：
- **s**：沿路径方向的**弧长**（纵向里程）
- **d**：垂直于路径的**横向偏移**（左正右负，即到中心线的距离）

它把任意弯道"拉直"成一条直线坐标轴——路径本身变成 s 轴。

**四项任务中的作用**：
1. **转弯降速**：路径曲率 κ 变为 s 的函数 κ(s)，规划时按 `v_max(s) = sqrt(a_lat_max / κ(s))` 生成速度剖面——曲率大的地方（κ 大）自动降速。
2. **判断道路偏离距离**：d 直接就是"偏离中心线多少米"，无需再做坐标变换；`|d| + 半车宽 > 半路宽` 即判定越界。
3. **收束可行路段**：道路在 Frenet 下是近似矩形的 (s, d) 区间，加上障碍物投影后，可行区域退化为若干段 (s 范围, d 范围)，裁剪与交集计算远比笛卡尔坐标下简单。
4. **输出可用路径**：规划器在 (s, d) 平面搜索/优化出轨迹，再通过 `path(s) + d·normal(s)` 逆变换回笛卡尔坐标点列，供控制器（Stanley）跟踪。

### 2. DP 代价需要考虑的因素

DP（动态规划）把路径搜索转成最小代价问题，代价函数通常加权求和：

$$J = w_1 J_{\text{len}} + w_2 J_{\text{curv}} + w_3 J_{\text{obs}} + w_4 J_{\text{road}} + w_5 J_{\text{smooth}} + w_6 J_{\text{goal}}$$

| 代价项 | 考虑内容 |
|---|---|
| 路径长度 | 越短越好，减少行驶时间 |
| 曲率/平滑度 | 大曲率急弯代价高（横向加速度大、需降速），二阶差分惩罚折角 |
| 障碍物距离 | 离障碍物越近代价越高（含裁剪后的可行路段边界、凸包） |
| 路面质量 | 地面平整度数据——颠簸路面代价高（数据来自传感器层的滤波取值） |
| 车道/路段保持 | 偏离可行路段中心、压边界代价高，收束约束的软化 |
| 目标点对齐 | 终点位置与方向偏差，保证接上下一段路径 |

还需考虑：**约束类**（转角限幅、横向加速度上限）以硬约束或高权代价形式进入；**权重标定**需与下游控制器能力匹配——DP 给出的路径若曲率超出控制器可执行范围，后续跟踪必然失败。

### 3. 规划器与控制器中传感器数据的参与

| 层级 | 需要的数据 | 来源 | 用途 |
|---|---|---|---|
| 规划 | 位姿 (x, y, yaw) | GPS/INS 融合 | 确定规划起点、路径投影 |
| 规划 | 障碍物点云/位置 | 激光雷达 / 视觉 | 凸包处理、裁剪、节点剪枝 |
| 规划 | 地面平整度 | 激光 / 视觉 | 代价函数的路面质量项 |
| 规划 | 车速 | 轮速 / 编码器 | 曲率限速、dp 代价权重 |
| 控制 | 车速 v | 编码器 | Stanley 分母与软化 |
| 控制 | 横摆角速度 r | IMU 陀螺仪 | 阻尼项 k_d(r − r_ref) |
| 控制 | 航向角 ψ | IMU + GPS 融合 | 航向误差 θ_e |
| 控制 | 转向角反馈 | 转角传感器 | 转向闭环、限幅确认 |
| 监控 | 时间戳 | 全传感器 | 延迟检测、时间对齐 |

### 4. 收束为一点的位置

该点是**前轴中心（front axle center）**。

理由：
- Stanley 控制器的横向误差定义为**前轴**到路径的垂距，规划起点与控制误差定义必须同点，否则跟踪会产生系统性偏差。
- 前轮是转向执行点，以后轴为原点还需额外做轴距几何换算。
- （若以质心或后轴为点，也可，但需与控制器误差定义保持一致并做轴距补偿；本车队架构按前轴中心。）

### 5. 信号大幅延迟的解决方案

**问题本质**：延迟使"测到的位置"是过去时刻的，车高速时位置误差 = v × Δt，基于滞后位姿的规划/控制全部失效。

分层对策：

1. **时间戳 + 延迟检测**：所有消息带时间戳，检测 `now − stamp` 超阈值即判为过期数据，**拒绝使用**而非直接喂给下游。
2. **状态预测补偿**：用 IMU（高频、低延迟）积分，把滞后的位置外推到当前时刻——GPS 慢、IMU 快，这是标准组合导航（GPS/INS 松耦合）思路。5 m/s 下 200 ms 延迟 = 1 m 误差，IMU 积分可在秒级内保持分米精度。
3. **多源融合 + 卡尔曼滤波**：以"预测 + 观测修正"框架融合 GPS/INS/轮速，预测用动力学模型，观测晚到就等到达时刻再做修正，同时估计延迟量。
4. **通信链路治理**：有线替无线、降低链路争用、检查时间同步（PTP/NTP），从源头降延迟。
5. **降级保护（fail-safe）**：延迟持续超限时切换安全模式——减速、停车、退出自主控制，**宁可停车也不执行错误输出**。
6. **闭环验证**：执行后用轮速/IMU 核对实际运动与指令是否一致，防止错误在链条中被逐级放大。

### 6. 完全自主驾驶算法（A* 等）

**A3（跟随预设路径）与 A5（完全自主）的区别**：A3 的路径来自实车预采集，规划器只做局部调整；A5 要求车**自己决定走哪**——感知、决策、规划全部在线完成。

**A\* 算法核心**：
$$f(n) = g(n) + h(n)$$
- g(n)：起点到当前节点的实际代价
- h(n)：当前节点到终点的启发式估计（曼哈顿/欧氏距离）
- h 可采纳（不高估）时 A* 保证最优；本质是 Dijkstra + 启发式剪枝

| 算法 | 特点 | 适用 |
|---|---|---|
| Dijkstra | 无启发、保证最优 | 小规模、无先验方向 |
| A* | 启发式搜索、最优 | 栅格/离散图，本题主选 |
| Hybrid A* | 状态含航向、考虑运动学 | 结构化道路、倒车入库 |
| RRT/RRT* | 随机采样、高维快 | 复杂环境、非结构化地形 |
| Lattice | 状态格子、动力学约束 | 与控制器能力匹配的轨迹 |

**完全自主的真正难点在系统级**：
1. **感知不确定性**：误检/漏检会传进规划，需四层策略（概率滤波、时序一致性、可行域裁剪、失稳降级）。
2. **时间对齐**：感知/规划/控制各自刷新率不同，整条链路的时间同步比单模块精度更关键。
3. **动态障碍物**：A* 是静态图搜索，实车需耦合预测模块（其他参与者未来 3~5s 轨迹）或用 D*/LPA* 增量重规划。
4. **实时性**：车在动，规划必须在毫秒级返回，否则路径生成出来车已过时。
5. **安全兜底**：规划失败或超时时必须有安全策略（刹停），不能"算不出来就随便给一条"。

## 题 05 ~ 09 　思维类（五选二，以下为参考思路）

### 题 05 　Ubuntu 版本选择

**为什么用 22.04 而不是 26：**

1. **LTS 长期支持**：22.04 是 LTS，官方维护 5 年（至 2027），26 是短期版，几个月后即停止更新——车队项目跨赛季，必须稳定维护。
2. **生态兼容是硬约束**：ROS 2 Humble 官方只支持 22.04；驱动（相机/LiDAR SDK）、CUDA、MATLAB/Simulink 接口、TSMaster 等都按固定版本验证过，新系统上大概率编译失败。
3. **可复现性**：全队统一版本，"在我机器上能跑"才能变成"在谁机器上都能跑"；换代意味着所有人重配环境、回归测试全部代码。
4. **新版本的收益 < 迁移成本**：新特性对车队无刚需，而迁移风险（隐性 API 变更、权限模型变化）要烧掉大量调试时间。

**工程软件使用要点**：
- 优先容器化（Docker）/ conda 隔离依赖，不污染系统 Python
- 装软件前查依赖与版本兼容矩阵，不盲目 `apt upgrade` 全系统
- 关键环境用快照/镜像备份，可回滚
- 记录安装步骤（文档化），不依赖"记忆里装过"
- 驱动与内核版本绑定时尤其谨慎，内核更新后先确认驱动仍可加载

### 题 06 　对数学的认识

参考框架：
1. **数学是建模语言**：把物理世界压缩成可推导的符号系统——控制律、代价函数、坐标变换背后全是数学。
2. **数学是工程的"先算后做"**：预算最坏情况（制动力、结构强度、跟踪误差上界），纸上先行，避免拿实车试错。
3. **数学提供思维品质**：证明训练的是"每一步都有依据"的严谨；这让写代码时重视边界条件与量纲。
4. **具体到规控**：微积分（误差积分、曲率）、线性代数（状态空间、滤波）、概率（融合与不确定度）是直接工具。
5. **坦诚的边界**：数学是地图不是领土，模型永远是近似——工程上要在"建模精度"与"计算实时性"间权衡，最后还要留安全余量。
6. **学习观**：不追求炫技，追求"能用数学把问题讲清楚并算出来"。

### 题 07 　大学展望与大学生活

参考框架（务必写自己的真实版本）：
1. **专业上**：把理论课与动手实践接起来——课程知识落到一个真实项目里才算学会。
2. **能力上**：通过车队这类工程项目练"从需求到可运行系统"的完整闭环（设计→实现→调试→复盘）。
3. **协作上**：学会代码评审、文档沟通、在团队中承担责任。
4. **节奏上**：平衡学业、项目与身体；保持可持续的节奏，不靠透支。
5. **想要的生活**：有明确目标、有产出、有复盘反思的生活；可具体到本学期要完成的 1~2 件有形成果。

### 题 08 　主人翁意识及其异化

1. **主人翁意识**：把自己视为事务的**主体与责任人**——"这是我的事，我来负责到底"。在车队中表现为：发现问题主动跟进、代码出错主动修复、不推诿、不等待分配。
2. **价值**：它是内驱力的来源，是工程文化（Ownership）的个人层面——工程上没有"这不归我管"，只有"系统还坏着"。
3. **被异化的主人翁意识**：形式上"像主人"，实质已偏离：
   - **表演式负责**：晒加班、刷存在感，而非真正把问题解决
   - **蛮干代替负责**：不沟通、不评估风险地"我说了算"，把责任变成独断
   - **自我物化**：把自身仅视为执行工具，只问"要我做什么"，不问"为什么做、该不该做"
   - **责任扩散的反面**：嘴上全包，实际无人对结果负责
4. **辨析标准**：真正的主人翁意识 = 主动担当 × 专业判断 × 团队协同；异化的表现则是把"身份姿态"当成"实际产出"。
5. **实践方式**：任务有 owner、代码有评审、结论有复盘——让"负责"可验证，而非口号。

### 题 09 　车队自动驾驶理解（图 3-1）

围绕五层数据流阐述（架构图同图 2-1）：

1. **整体是"感知 → 规划 → 控制 → 执行"的分层流水线**，每层只做一件事，靠明确接口交接：文件层提供预采集路径与参数 → 传感器层产出可用的环境与位姿数据 → 规划层算出路径 → 控制层算出指令 → 车机层执行。
2. **规划层是核心**：实时规划器先做**预处理**（凸包处理、以车长半宽裁剪障碍物、可行性路段、滤波、地面平整度），再**收束可行路段 → 障碍物节点剪枝 → DP 规划路线 → 路径平滑 → 输出路径**——从"哪里能走"逐步收敛到"走哪条"。
3. **控制层是横向 + 纵向解耦**：横向用 Stanley（转角输出），纵向按路面情况与预期速度给电机；规划给轨迹，控制负责跟上。
4. **A3 与 A5**：A3 跟随预采集路径（图中路径文件的来源是实车采集 + GPS/INS），A5 完全自主需在线感知决策，是更高目标。
5. **工程上的关键认识**：数据流上每一环都有延迟与误差，整条链路的**时间对齐与降级保护**比单点精度更重要；信号延迟会导致下游全错（见题 04 第 5 问）。
6. **结合自身**（若有）：指出自己在感知/控制某一环可以贡献什么，以及想补哪块短板。
