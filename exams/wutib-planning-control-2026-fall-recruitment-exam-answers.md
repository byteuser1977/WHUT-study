## 题 01 　开环 / 闭环速度控制

### 1. 哪个是闭环、哪个是开环？

我看了图 1-1：上面那条链路，期望速度进去以后经下位机、电机直接输出实际速度，中途没有回头的线，这是开环；下面那条链路多了一个反馈回路，实际速度被送回控制器和期望速度对比，拿偏差去驱动控制器，这就是闭环。

比赛里我觉得闭环更合适。我们场地经常换，草地、沙地、泥地的摩擦力都不一样，电池越跑电压越低，电机出力也会变，再算上载人和空车的差别——同样的指令下去，实际速度完全可能不一样。开环是"发完指令就不管了"，这些干扰它根本兜不住；闭环至少能靠速度反馈一直纠，把实际值往期望值上拽。而且赛规对速度和轨迹有要求（比如 A3 跟随路径），这种要求开环基本没法保证。

### 2. 哪一种拟合度更高？

肯定是闭环那个。道理跟上面差不多：不管什么原因让实际速度偏离了期望值，偏差都会被反馈回来，控制器接着调，慢慢把误差压回去。如果用控制书里的话讲，闭环能把稳态误差压到趋近于零，还能抗干扰；开环则完全看模型准不准，误差就是原样留着，甚至会越积越大。

### 3. 强化学习和闭环控制的联系

这个我之前做项目时想过一阵。两者看着一个属于控制、一个属于 AI，但骨架其实很像，都是"观察 → 决策 → 执行 → 拿到反馈"这样转圈：

| 环节 | 闭环控制 | 强化学习 |
|---|---|---|
| 状态获取 | 传感器测量 | 环境观察 observation |
| 反馈信号 | 偏差 e = 期望 − 实际 | 奖励 r |
| 决策 | 控制律（PID、Stanley 之类） | 策略 π(a\|s) |
| 执行 | 执行器动作 | 环境 step |
| 目标 | 让跟踪误差尽量小 | 让累积奖励尽量大 |

我觉得它们的区别主要在"控制律是怎么来的"：闭环的控制律是人推公式、人调参数调出来的，好处是能解释、能验证；强化学习是让机器自己试错学出来的，好处是能处理那种很难建模的复杂系统，比如四足机器人走路、机械臂抓东西。但它样本效率低，安全性也不好保证。

工程上我见过的常见做法是两者结合：让 RL 去学控制律或者参数，外面再套一层经典控制管安全边界和限幅，出问题时兜得住。

## 题 02 　技术基础

### 1. ROS 2 部署环境与术语

ROS 2 主要跑在 Linux 上，官方首选 Ubuntu，我们车队统一用 22.04 LTS（对应 ROS 2 Humble）。它其实也支持 Windows、macOS，树莓派这类嵌入式平台也有支持，但那些属于 Tier 3，社区踩坑的少。机器人开发这一圈，事实标准就是 Ubuntu。

这几个术语我按自己的理解写：

| 术语 | 我的理解 |
|---|---|
| 节点 Node | 一个独立跑起来的程序，只干一件事，比如一个节点管激光雷达驱动，一个管路径跟踪 |
| 订阅 Subscribe | 从某个话题上收消息的动作 |
| 发布 Publish | 往某个话题上发消息的动作 |
| 时间戳 Timestamp | 消息里带的产生时刻，用来把多个传感器的数据对到同一时刻，也能用来发现数据过期 |
| 消息 Message | 话题里传的数据结构，比如 Twist、PoseStamped，是用 `.msg` 文件定义的 |
| 定时器 Timer | 按固定周期触发回调，比如控制循环 100Hz 就用它 |
| 生命周期节点 Lifecycle | 带状态机的节点（Unconfigured→Inactive→Active→Finalized），好处是能统一启停、出错好恢复 |
| 话题 Topic | 节点之间异步通信的命名通道，发布/订阅模型，一个话题上可以有很多发布者和订阅者 |
| 回调 Callback | 消息到了或者定时器到点之后被调用的处理函数，由执行器调度到对应线程去跑 |

### 2. SSH 连接与网线直连

SSH 我理解就是"安全的远程终端"：它把你的操作加密以后发到另一台机器上执行，正好适合我们把电脑上的代码部署到车上跑。默认端口是 22，除了远程登录，还能传文件（scp、rsync），也能转发图形界面，做到"代码在车上跑、人在车边改"。

两台电脑只用一根网线传信息，我按自己的步骤试过：

1. 先拿网线把两个网口接起来。现在的网口一般都支持 Auto-MDIX，普通网线就行；老机器可能得用交叉线。
2. 给两台机器手动配同网段的 IP。这里有个坑：直连时没有 DHCP 服务器，等着自动分配是拿不到地址的。
   ```bash
   # 电脑 A
   sudo ip addr add 192.168.1.1/24 dev eth0
   # 电脑 B
   sudo ip addr add 192.168.1.2/24 dev eth0
   ```
   （网卡名不一定是 eth0，用 `ip link` 先看一眼。）
3. 互相 ping 一下确认通了：`ping 192.168.1.2`
4. 目标机装好并启动 sshd，防火墙放行 22 端口。
5. 登录：`ssh user@192.168.1.2`，第一次会问你确认指纹，输密码就行（配了密钥就免密）。
6. 传文件：`scp ./code.py user@192.168.1.2:~/`，文件夹多的话 `rsync -av ./code/ user@192.168.1.2:~/code/` 更好用。

### 3. 双系统与虚拟机

这两个我都用过，差别主要在性能和硬件能不能直接摸到：

| 对比项 | 双系统 | 虚拟机 |
|---|---|---|
| 是什么 | 电脑里装两套系统，开机时选一个进 | 在 Windows 里再模拟出一台电脑跑 Linux |
| 性能 | 直接跑在硬件上，没有损耗 | 有虚拟化开销，显卡这类硬件用得不太好 |
| 硬件访问 | 所有硬件都能直接用 | 部分受限，USB 设备要额外配置直通 |
| 切换 | 得重启，一次只能跑一个 | 随时切，能跟 Windows 并存 |
| 磁盘 | 要单独分区，装错了有风险 | 一个镜像文件，删掉就是卸载 |
| 安全性 | 改坏了影响整个系统 | 有快照，弄坏了可以回滚 |

用在哪我这么判断：学 Linux、跑跑轻量代码、需要一边看 Windows 资料一边干活，虚拟机够用了，而且安全；但接传感器（USB 摄像头、激光雷达）、做实车部署、对实时性有要求的场景，必须上双系统，不然硬件这关就过不去。

### 4. Git 与工作区

Git 是个分布式版本控制系统，记录文件每次改动的历史，可以回滚、开分支、合并多人的修改。分布式的意思是每台机器上都有完整的仓库，没网也能用。

它的核心其实就三大区，再加一个远程仓库：

| 区域 | 作用 |
|---|---|
| 工作区 Working Directory | 我们直接编辑文件的那个目录，改动还没被记录 |
| 暂存区 Staging Area | `git add` 之后改动进到这里，相当于下一次提交的草稿 |
| 仓库 Repository | `git commit` 之后快照就永久存进 `.git`，随时能翻历史 |
| 远程仓库 Remote | 放在 GitHub/Gitee 上的共享副本，严格说不算本地三大区，用 `git push/pull` 跟它同步 |

### 5. GitHub 与 Git 的区别

| | Git | GitHub |
|---|---|---|
| 本质 | 装在本地的版本控制工具 | 托管 Git 仓库的网站 |
| 要不要网 | 不要 | 要 |
| 干什么 | 管版本、分支、合并、查历史 | 在这些基础上加了 PR 评审、Issue、Actions 自动化、权限管理 |

我觉得团队必须要用 GitHub（或者 Gitee 这类平台）。理由很简单：代码得有个统一的存放地，不然大家靠 U 盘互相拷，早晚出事；分支 + Pull Request 这套流程能把"写代码 → 评审 → 合并"走成规矩，避免互相覆盖；谁改了什么、为什么改，历史里都翻得出来；再配上 Actions，每次推送自动编译测试一遍，就不会把编译不过的代码带进主干。

## 题 03 　带阻尼 Stanley 控制器

### 1. 我对 Stanley 的认识

Stanley 是横向路径跟踪里最经典的算法之一，最早是斯坦福参加无人驾驶挑战赛那一队搞出来的，专门针对前轮转向的车。它的思路特别直观：一边把车头摆正（修正航向偏差 θ_e），一边往路径中间靠（修正横向偏差 e），两件事一起做，车就既对得准方向又贴得住线。

我觉得它最漂亮的一点是横向项 `arctan2(k_e·e, v)`：低速时这个增益很大，纠偏很猛；速度上去了增益自动变小，不会横冲直撞，天生就带速度自适应。

代码里还加了几个工程上的补丁：
- `k_s` 低速软化：把分母写成 `|v| + k_s`，不然车停着的时候就除零了，而且低速增益会爆炸。
- 阻尼项 `k_d(r − r_ref)`：拿实际横摆角速度跟路径曲率算出来的期望横摆率 `r_ref = v·κ` 比一下，差得越多就越往回压，专门治大曲率、高速下横摆发抖的毛病。
- `_wrap` 角度归一化：把航向差折回 [−π, π]，不然角度跳过 ±360° 会直接把转向打反。
- 转角限幅 clip 到 ±40°，别让指令超出机械能走的范围。

要说短板，它本质还是几何方法，不考虑轮胎侧偏这类动力学特性，高速、大曲率下精度会掉下来——加阻尼项就是为此打的补丁，但极限工况下还是不如 MPC 那种把动力学模型写进优化里的做法。

### 2. 代码对应的公式

我把代码一行行对成了公式，一共八步：

**① 最近路径点**
$$idx = \arg\min_i \left[(x_i - x)^2 + (y_i - y)^2\right]$$

**② 角度归一化**
$$\text{Wrap}(\alpha) = (\alpha + \pi) \bmod (2\pi) - \pi$$

**③ 航向误差**
$$\theta_e = \text{Wrap}\left(\theta_{\text{path},idx} - \psi\right)$$
这里 ψ 就是代码里的 yaw。

**④ 横向误差**
$$e = -(x_{idx} - x)\sin\psi + (y_{idx} - y)\cos\psi$$

严格说这个式子是把"车辆指向最近路径点"的向量投影到车辆的横向轴（左边，方向是 $(-\sin\psi, \cos\psi)$）上，代码拿它当"前轴到路径的垂距"用。两者在路径切向和车头朝向差不多的时候是一致的，这也正是 Stanley 只做局部跟踪、要先搜最近点的原因。

**⑤ 低速软化后的有效速度**
$$v_{\text{eff}} = |v| + k_s$$

**⑥ Stanley 主项**
$$\delta_{st} = \theta_e + \arctan2\!\left(k_e \cdot e,\ v_{\text{eff}}\right)$$

代码用的是 `np.arctan2(y, x)`，数学上跟 `arctan(y/x)` 是一回事，但它能处理分母的符号、不怕除零，输出还稳定在 $(-\pi, \pi]$，写工程代码更合适。

**⑦ 阻尼修正**（r 是实际横摆角速度，κ 是路径曲率）
$$r_{\text{ref}} = v \cdot \kappa_{idx}$$
$$\delta = \delta_{st} - k_d\,(r - r_{\text{ref}})$$

**⑧ 限幅**
$$\delta_{\text{final}} = \text{clip}\left(\delta,\ -\delta_{\max},\ \delta_{\max}\right),\quad \delta_{\max} = 40°$$

默认参数是：k_e = 0.6，k_s = 1.0 m/s，k_d = 0.10 s，δ_max = 40°。顺带一提单位是对得上的：k_d 乘以角速度差（rad/s）正好得到角度，所以 k_d 的单位是秒。

## 题 04 　系统架构与规控

### 1. Frenet 坐标系

Frenet 坐标系是沿着参考路径建的局部坐标系，名字来自法国数学家 Jean Frédéric Frenet（Frenet–Serret 公式就是他提的）。它只用两个量描述位置：
- **s**：沿着路径走过的弧长，就是"开了多远"
- **d**：垂直于路径的横向偏移，左正右负，就是"偏了多远"

好处是一下子把弯道拉直了——路径本身成了 s 轴，后面所有计算都在这条"直线"上做。

题目问的四件事，我是这么理解它怎么起作用的：

1. **转弯降速**：曲率 κ 在 Frenet 下就是 s 的函数 κ(s)，速度按 `v_max(s) = sqrt(a_lat_max / κ(s))` 铺出去，弯越急（κ 越大）允许的速度越低，自动就降下来了。
2. **判断道路偏离距离**：d 本身就是"离中心线几米"，连坐标变换都省了；`|d| + 半车宽 > 半路宽` 就算出界。
3. **收束可行路段**：路在 Frenet 下基本是个矩形的 (s, d) 区间，把障碍物投影上去之后，能走的部分就退化成几段 (s 范围, d 范围)，裁剪和求交都比在笛卡尔坐标里算简单太多。
4. **输出可用路径**：规划器在 (s, d) 平面里搜出轨迹，再用 `path(s) + d·normal(s)` 变回一串笛卡尔坐标点，交给 Stanley 去跟。

### 2. DP 代价要考虑哪些

DP 是把找路径变成"总代价最小"的问题，代价一般写成几项加权和：

$$J = w_1 J_{\text{len}} + w_2 J_{\text{curv}} + w_3 J_{\text{obs}} + w_4 J_{\text{road}} + w_5 J_{\text{smooth}} + w_6 J_{\text{goal}}$$

| 代价项 | 为什么要算它 |
|---|---|
| 路径长度 | 越短越好，省时间 |
| 曲率/平滑度 | 急弯代价高（横向加速度大、还得降速），二阶差分可以惩罚折角 |
| 障碍物距离 | 离障碍物越近代价越高（包括裁剪后的边界、凸包） |
| 路面质量 | 地面平整度数据，颠簸路面代价高 |
| 车道/路段保持 | 偏离可行路段中心、压边代价高，相当于把收束约束软化 |
| 目标点对齐 | 终点位置和方向别差太多，不然接不上下一段路 |

除了这些软代价，还有硬约束（转角上限、横向加速度上限）要么直接限死，要么给个极大的权重。另外权重要跟下游控制器的能力对上——DP 给出的路径要是曲率大到控制器跟不住，后面怎么调都是白搭。

### 3. 哪些流程要用到传感器数据

| 层级 | 要的数据 | 哪来 | 干什么 |
|---|---|---|---|
| 规划 | 位姿 (x, y, yaw) | GPS/INS 融合 | 定规划起点、做路径投影 |
| 规划 | 障碍物点云/位置 | 激光雷达、视觉 | 凸包处理、裁剪、节点剪枝 |
| 规划 | 地面平整度 | 激光、视觉 | 给代价函数提供路面质量项 |
| 规划 | 车速 | 轮速、编码器 | 曲率限速、DP 代价权重 |
| 控制 | 车速 v | 编码器 | Stanley 的分母和软化 |
| 控制 | 横摆角速度 r | IMU 陀螺仪 | 阻尼项 k_d(r − r_ref) |
| 控制 | 航向角 ψ | IMU + GPS 融合 | 算航向误差 θ_e |
| 控制 | 转向角反馈 | 转角传感器 | 转向闭环、限幅确认 |
| 监控 | 时间戳 | 所有传感器 | 延迟检测、时间对齐 |

### 4. 车被收束成的那个点在哪

我们这套架构取的是**前轴中心**。代码注释里也写明白了"横向误差：前轴到路径的垂距"，规划起点和控制器算误差用的是同一个点，这样才不会凭空多出一个固定偏差。

为什么这个点必须统一：Stanley 的横向误差是按前轴定义的，规划要是拿别的点当起点，两边的基准就对不上，跟踪会带一个系统性的偏。而且前轮本来就是转向执行点，拿它当原点建模最直接，不用再做轴距换算。

不过面试如果追问，我也准备好说别的选法：运动学自行车模型天然定义在后轴，所以动力学规划常拿后轴中心当参考点，但那样就得先做轴距旋转再喂给 Stanley；质心则便于算离心力、横向加速度约束，但要知道前后轴载荷怎么分。说到底，选哪个点都能对，前提**是规划、控制、状态估计三家用的参考点一致**，或者中间做了显式转换。

### 5. 信号大幅延迟怎么办

这个问题的本质是：延迟意味着"测到的位置"是过去某一刻的，车速快的时候位置误差 = v × Δt，拿这种滞后数据去做规划和控制，后面全都会错。我按层次想了几步：

1. **打时间戳、判过期**：所有消息带时间戳，`now − stamp` 超过阈值就认为数据过期，直接拒用，别往下游喂。工程上这个阈值我见过常用的大概是 100~200 ms，具体要看车速和控制频率。
2. **用 IMU 往前推**：IMU 频率高、延迟低，拿它积分可以把滞后的 GPS 位置外推到当前时刻。比如 5 m/s 下延迟 200 ms 就是 1 m 误差，光靠 GPS 兜不住，但 IMU 积分在秒级尺度上还能保持分米级精度——这其实就是 GPS/INS 松耦合的思路。
3. **多源融合 + 卡尔曼滤波**：用"预测 + 观测修正"的框架把 GPS、INS、轮速揉在一起，预测走动力学模型，观测晚到就在到达的时刻做修正，顺便把延迟量也估计出来。
4. **从源头降延迟**：能走有线就别用无线，查查链路有没有争用，时间同步（PTP/NTP）是不是做对了。
5. **降级保护**：延迟一直超限就切安全模式——减速、停车、退出自主，宁可停车也别拿错误数据硬跑。
6. **回头验证**：执行之后拿轮速、IMU 核一下实际运动和指令对不对得上，防止错误在链条里被一级级放大。

### 6. 完全自主驾驶算法（A* 等）

先分清 A3 和 A5：A3 是跟预设路径，路径是实车提前采集好的，规划器只做局部调整；A5 是完全自主，车要自己决定走哪条，感知、决策、规划全都得在线完成。

A* 是我最熟的全局搜索算法，核心就是这一行：
$$f(n) = g(n) + h(n)$$
- g(n)：起点走到当前节点实际花了多少
- h(n)：从当前节点到终点的估计值（用曼哈顿距离或欧氏距离）
- 只要 h 不高估（可采纳），A* 就保证找到最优解；可以理解成 Dijkstra 加了个启发式剪枝

其它几个我也了解过：

| 算法 | 特点 | 用在哪 |
|---|---|---|
| Dijkstra | 没有启发式，全量搜，肯定最优 | 地图小、没有方向先验 |
| A* | 有启发式，最优 | 栅格地图，这类题的首选 |
| Hybrid A* | 状态里带航向，考虑运动学 | 结构化道路、倒车入库 |
| RRT / RRT* | 随机采样，高维下很快 | 复杂环境、非结构化地形 |
| Lattice | 状态格子，满足动力学约束 | 要求轨迹和控制器能力匹配的场景 |

但我觉得完全自主的难点真不在单个算法上，而在系统层面：

1. **感知不确定**：误检、漏检会一路传进规划，得有几层兜底（概率滤波、时序一致性、可行域裁剪、失稳降级）。
2. **时间对齐**：感知、规划、控制刷新率都不一样，整条链路的时间同步比单个模块的精度还关键。
3. **动态障碍物**：A* 是静态图搜索，实车得配上预测模块（估计别人未来 3~5 秒的轨迹），或者用 D*、LPA* 这类增量重规划。
4. **实时性**：车一直在动，规划必须毫秒级出结果，不然路算出来车早过去了。
5. **安全兜底**：规划失败或者超时，必须有刹车停车这类安全策略，不能"算不出来随便给一条"。

## 题 05 ~ 09 　思维类（五选二，下面只是我的思路，别照抄）

### 题 05 　Ubuntu 版本选择

我觉得我们用 22.04 而不是 26，理由主要不是新旧，而是稳不稳：

1. 版本成熟度上：22.04 是 LTS，2022 年 4 月发的，标准维护到 2027 年 4 月，现在还在支持期里。26.04 其实也是 LTS（Ubuntu 偶数年的 .04 版都是 LTS），但它刚发出来不到半年，属于生态灰区——第三方库、驱动、工具链还没跟上。我们项目要跨赛季跑，选一个踩过坑的成熟版本，比追新靠谱得多。
2. 生态兼容是硬约束：ROS 2 Humble 官方就定在 22.04；相机、激光雷达的 SDK、CUDA、MATLAB/Simulink 接口、TSMaster 这些都在固定版本上验证过，换新系统大概率编译不过。
3. 可复现性：全队一个版本，才谈得上"在我机器上能跑 = 在谁机器上都能跑"。换版本意味着所有人重配环境、所有代码回归一遍。
4. 收益赶不上成本：新版本的特性我们用不上，但迁移的隐性风险（API 变了、权限模型变了）得花大量时间去摸。

工程软件使用上，我自己的习惯是：能容器化（Docker）或者 conda 隔离依赖就隔离，别污染系统 Python；装之前先查依赖和兼容矩阵，别盲跑 `apt upgrade` 全系统升级；关键环境留个快照，装坏了能退回来；安装步骤写成文档，别只靠记忆；驱动和内核版本绑定的时候尤其要小心，内核更新后先确认驱动还加载得了。

### 题 06 　对数学的认识

我的看法是：

1. 数学是一门"建模语言"，它把现实世界压缩成可以推导的符号——我们写控制律、代价函数、坐标变换，背后全是数学。
2. 数学让我们能"先算后做"：制动力够不够、结构强度够不够、跟踪误差上界多少，都能在纸上先估出来，不用拿实车去试错。
3. 数学还训练思维习惯。证明题逼着人每一步都有依据，我写代码时因此会更在意边界条件和量纲。
4. 具体到规控：微积分（误差积分、曲率）、线性代数（状态空间、滤波）、概率（融合与不确定度）都是天天要用的工具。
5. 但我也不想神化它。数学是地图不是领土，模型永远是近似，工程上得在建模精度和实时性之间取舍，最后还得留安全余量。
6. 学数学我追求的是"能用它把问题讲清楚并且算出来"，不追求炫技。

### 题 08 　主人翁意识及其异化

我的理解：

主人翁意识是把自己当成事情的主体和责任人——"这是我的事，我要负责到底"。放到车队里就是发现问题主动跟进、代码出错主动修、不推诿、不等着别人来分配。它的价值在于提供内驱力，也是工程文化里 Ownership 的个人那一面：工程上没有"这不归我管"，只有"系统还坏着"。

但也有走偏的情况，就是被异化的主人翁意识，表面上像主人，实际上已经变了味：

- 表演式负责：晒加班、刷存在感，但问题没真正解决
- 蛮干代替负责：不沟通、不评估风险地"我说了算"，把责任变成独断
- 自我物化：把自己只当成执行工具，只问"要我做什么"，不问"为什么做、该不该做"
- 嘴上全包、实际没人对结果负责

我的判断标准是：真正的主人翁意识 = 主动担当 × 专业判断 × 团队协同，而异化则是把"身份姿态"当成"实际产出"。落到实践上，任务要有 owner、代码要有评审、结论要有复盘，让"负责"可以被验证，而不是停在口号。

### 题 09 　车队自动驾驶理解（图 3-1）

对着架构图，我的理解是这样的：

整体上它是一条"感知 → 规划 → 控制 → 执行"的分层流水线，每层只干一件事，靠明确的接口交接。文件层提供预采集的路径和参数，传感器层产出可用的环境和位姿数据，规划层算出路径，控制层算出指令，车机层去执行。

规划层是核心。实时规划器先做预处理（凸包处理、按车长半宽裁剪障碍物、可行性路段、滤波、看地面平整度），再收束可行路段、对障碍物节点剪枝、用 DP 规划路线、平滑，最后输出路径——其实是从"哪里能走"一步步收敛到"走哪条"。

控制层是横向、纵向解耦的：横向用 Stanley 输出转角，纵向按路面情况和预期速度给电机。规划给的是轨迹，控制负责把它跟上。

A3 和 A5 的关系我也想明白了：A3 跟随预采集的路径（路径文件就是实车采集 + GPS/INS 得来的），A5 完全自主要在线感知决策，是更高的目标。

我觉得工程上最要紧的认识是：数据流每一环都有延迟和误差，整条链路的时间对齐和降级保护，比某个模块精度多高更重要——信号一延迟，下游全跟着错（跟题 04 第 5 问是同一件事）。

最后如果要说我自己，我比较感兴趣控制这一环，想从横向跟踪这块入手补，比如先把 Stanley 的参数整定做熟。
